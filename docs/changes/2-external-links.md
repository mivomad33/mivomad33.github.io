# 변경 2: 외부 링크를 새 탭으로 열기

- 상태: 완료(2026-10-21). 기획·설계는 사용자가 [결정](#결정)을 모두 추천안으로 확정했고, 하위 단계 1(시안)·2(구현)를 마친 뒤 변경 전체가 사용자 검토를 통과해 main에 squash merge했다.
- 브랜치: `change/external-links`

## 배경

- 지금은 모든 링크가 현재 탭에서 열린다. 외부 링크를 따로 처리하는 코드가 없어 브라우저 기본 동작을 그대로 따르기 때문이다.
- 사용자는 글이나 포트폴리오를 보다가 외부 링크(GitHub, 프로젝트 데모, 글 본문 속 참고 링크)를 누르면 보던 화면이 갑자기 다른 사이트로 바뀌어 불편하다고 느꼈다(2026-10-21 사용자 의견).
- 사용성 연구(NN/g 등)는 새 탭을 강제하지 말라고 권하지만, 개인 블로그·포트폴리오는 대부분 외부 링크만 새 탭으로 연다. 읽던 글로 돌아오기 쉽고, 방문자가 사이트를 떠나지 않기 때문이다. 이 사이트는 글을 읽다가 참고 링크를 누르는 일이 많아 후자를 따른다.

## 요구사항

### 해야 하는 것

- 외부 링크는 새 탭에서 연다. 사이트 안 링크는 지금처럼 현재 탭에서 연다.
- 외부 링크에는 새 탭에서 열린다는 표시를 둔다. 눈에 보이는 표시(아이콘)와 화면 낭독기가 읽는 문구 둘 다다(누르기 전에 새 탭이 열린다는 것을 알 수 있게 하는 접근성 권고를 따른다).
- 사이트의 모든 외부 링크에 같은 규칙이 적용된다. 컴포넌트에서 쓰는 링크(포트폴리오 카드, 소개 페이지, 푸터)와 글 본문(md)의 링크를 모두 포함한다.
- 외부 링크인지 판단하는 규칙, 붙는 속성, 표시 모양은 각각 한 곳에서만 정한다(아래 [공통화](#공통화)).
- 규칙을 지키지 않은 링크가 생기면 빌드가 실패한다.

### 하지 않는 것

- 사이트 안 링크(메뉴, 글 목록, 이전·다음 글, 언어 전환 링크, `/`로 시작하는 데이터 링크)는 바꾸지 않는다.
- `mailto:` 링크는 바꾸지 않는다. 브라우저 탭이 아니라 메일 앱이 열리므로 새 탭이 필요 없다.
- 사용자가 새 탭 여부를 고르는 설정은 두지 않는다(Cmd/Ctrl+클릭으로 이미 고를 수 있다).
- 클라이언트 JS는 쓰지 않는다(design.md 코드 규칙). 모두 빌드할 때 HTML에 넣는다.

## 설계

### 외부 링크 판단

- 외부 링크: 주소를 사이트 주소(`SITE`) 기준으로 해석한 결과(`new URL(href, SITE)`)의 프로토콜이 `http:`나 `https:`이고, 호스트가 사이트 주소의 호스트와 다른 링크.
  - 글자로 `http://`·`https://`로 시작하는지 보지 않고 해석한 결과를 보는 이유: 브라우저가 실제로 해석하는 방식과 같게 판단하기 위해서다. 글자로 보면 프로토콜을 뺀 `//example.com/...`이 상대 주소로, 대문자로 쓴 `HTTPS://...`가 외부가 아닌 것으로 잘못 나뉘어, 다른 사이트인데 현재 탭에서 열리고 빌드 결과 검사도 통과한다(데이터 파일은 스키마가 `//`를 막지만 글 본문은 막는 곳이 없다. 2026-10-21 검토에서 나왔다).
- 그 밖은 모두 외부가 아니다: `/`로 시작하는 사이트 안 주소, `#`로 시작하는 페이지 안 이동, 상대 주소, `mailto:`(해석한 프로토콜이 `mailto:`).
- 사이트 주소로 시작하는 절대 주소(예: 글 본문에 사이트 주소를 통째로 적은 링크)는 사이트 안 링크로 본다. 8단계에서 `SITE`를 바꾸면 따라 바뀐다.

### 붙는 속성

- `target="_blank"`와 `rel="noopener"`.
  - `noopener`: 새 탭의 페이지가 이 페이지를 조작하지 못하게 한다. 지금 브라우저는 `_blank`에 기본으로 적용하지만, 오래된 브라우저를 위해 적는다.
  - `noreferrer`는 붙이지 않는다. 붙이면 이동한 사이트가 이 사이트에서 왔다는 것(referrer)을 모른다. 공개 블로그라 숨길 정보가 없고, 사용자의 GitHub 저장소 통계(Traffic의 Referring sites)처럼 유입 경로를 보는 곳에서 이 사이트가 보이는 편이 낫기 때문이다. 처음 답변에서는 `noopener noreferrer`를 말했지만 이 이유로 바꿨다. [결정](#결정)에서 확정했다.

### 표시

- 눈에 보이는 표시(하위 단계 1의 시안 B안, 2026-10-21 사용자 승인): 링크 글자 바로 뒤에 작은 SVG 아이콘(상자에서 나가는 화살표)을 둔다.
  - 크기: 폭 0.8em(링크 글자 크기를 따른다), 링크 글자와의 간격 `--spacing`의 1배.
  - 색: 링크 글자와 같은 색(`currentColor`)이라, 강조색 링크에서는 강조색, 푸터처럼 흐린 링크에서는 흐린 글자색이고, 마우스를 올려 링크 색이 바뀌면 함께 바뀐다.
  - 포트폴리오 카드 링크: 앞 기호 `→`는 그대로 두고 뒤에 아이콘을 더한다.
  - 글 본문 링크: 밑줄은 링크 글자에만 있고 아이콘에는 없다.
  - 고르지 않은 안과 이유: A안(`↗` 글자 기호)은 포트폴리오 카드 링크에 이미 앞 기호 `→`가 있어 화살표 두 개가 헷갈려 보인다(사용자 의견). C안(작고 흐린 `↗`)도 같은 글자 기호다. 카드 링크의 앞 기호를 `↗`로 바꾸는 안도 고르지 않았다.
  - 구현 조건(줄바꿈, 밑줄, 마크업 구조)은 [진행 계획](#진행-계획) 하위 단계 1에 적었다.
- 화면 낭독기 문구: 링크 이름 뒤에 "(새 탭에서 열림)", 영어 페이지는 "(opens in a new tab)"을 읽힌다. 문구는 언어별 사전(`src/lib/i18n.ts`의 `UI`)에 둔다(design.md 코드 규칙).
  - 문구는 아이콘의 이름으로 둔다(아이콘에 `role="img"`와 `aria-label`). 처음에는 아이콘을 화면 낭독기에서 숨기고(`aria-hidden`) 문구를 숨긴 글자(`sr-only` span)로 두었는데, 검토(2026-10-21, 서브에이전트)에서 제목 안의 외부 링크가 있으면 제목 id(앵커)에 문구가 섞이는 것을 찾았다(`## [Astro](...) 소개` → `id="astro-새-탭에서-열림-소개"`). Sätteri가 제목 id 플러그인을 사용자 플러그인 뒤에 실행해, 숨긴 글자까지 제목 글자로 읽기 때문이다. 나중에 목차를 만들면 목차 글자에도 섞인다. 속성은 글자가 아니므로 섞이지 않고, 화면 낭독기는 여전히 링크를 "링크 이름 (새 탭에서 열림)"으로 읽는다(사용자 결정, 2026-10-21).

### 공통화

외부 링크 처리를 쓰는 곳마다 구현하지 않고 공통으로 만든다(2026-10-21 사용자 의견, CLAUDE.md 작업 규칙). 다만 글 본문(md)은 마크업을 직접 쓰지 않아 컴포넌트를 쓸 수 없으므로, 규칙·속성·모양을 한 곳에 두고 그것을 쓰는 입구를 두 개(컴포넌트, md 플러그인) 둔다.

- 규칙과 속성(`src/lib/link.ts`): 외부 링크인지 판단하는 함수(`isExternalUrl`)와 붙일 속성 값(`target`, `rel`). 아래 두 입구와 빌드 결과 검사가 모두 이것을 쓴다.
- 입구 1, 링크 컴포넌트(`src/components/Link.astro`): 주소를 받아 외부면 속성과 표시를 붙이고, 아니면 일반 `<a>`를 만든다.
  - "외부 링크 컴포넌트"가 아니라 모든 링크를 받는 컴포넌트로 만든다([결정](#결정)). 데이터 파일의 링크(`url`)는 외부 주소일 수도, 사이트 안 주소(`/blog/...`)일 수도 있어, 쓰는 곳이 미리 알 수 없기 때문이다. 쓰는 곳은 주소만 넘기고 판단은 컴포넌트가 한다.
  - 지금 바꿀 곳: 포트폴리오 카드(`PortfolioCard.astro`), 소개 페이지의 링크 목록, 푸터의 링크 목록(`BaseLayout.astro`). 메뉴·글 목록처럼 항상 사이트 안 주소인 링크는 바꾸지 않아도 되지만, 앞으로 데이터에서 오는 주소는 이 컴포넌트로 쓴다.
  - 링크마다 다른 클래스(강조색, 흐린 글자색 등)는 지금처럼 쓰는 곳이 넘긴다. 컴포넌트는 외부 링크에 관한 것만 붙인다.
- 입구 2, md 플러그인(`src/lib/markdown-external-links.ts`. Astro 기본 마크다운 처리기 Sätteri의 hast 플러그인으로, `astro.config.mjs`의 `markdown.processor`에 넣는다): 글 본문의 `<a>`에 같은 함수로 판단해 같은 속성과 표시를 붙인다.
  - 처음에는 rehype 플러그인(`markdown.rehypePlugins`)으로 계획했지만, Astro 7은 기본 처리기가 Sätteri로 바뀌어 rehype 플러그인을 쓰려면 예전 처리기(unified, `@astrojs/markdown-remark`)를 따로 설치해 처리기 전체를 바꿔야 했다(구현 중 확인). Sätteri의 hast 플러그인은 rehype와 같은 AST(hast)를 다루고 글 파일 경로(`ctx.fileURL`)도 받으므로 이것으로 했다. 처리기를 설정하려고 `@astrojs/markdown-satteri`(Astro가 고정한 버전과 같게 고정)와 `satteri`를 직접 의존성으로 더했다(design.md 기술 스택).
  - 외부 패키지(`rehype-external-links`)도 있지만 직접 만든다([결정](#결정). 위 이유로 rehype 패키지는 어차피 쓸 수 없게 됐다). 판단 규칙과 표시 마크업을 컴포넌트와 같은 것으로 쓰려면 어차피 설정을 대부분 직접 넘겨야 하고, 하는 일이 작아(링크 속성 붙이기) 의존성을 늘릴 만큼이 아니기 때문이다.
  - 아이콘 이름(화면 낭독기 문구)의 언어는 글 파일 이름(`ko.md`, `en.md`)으로 정한다.
- 표시 모양: 아이콘의 모양(크기, 색, 간격)은 한 곳(`global.css`의 클래스 하나 등)에서만 정하고, 컴포넌트와 플러그인은 같은 클래스·마크업을 붙인다. 정확한 방식은 하위 단계 2에서 시안을 구현하며 정한다.

### 검사

- 빌드 결과 검사(`scripts/check-build.ts`)에 더한다: 모든 페이지의 `<a>` 가운데 외부 링크는 정한 속성과 표시가 있고, 외부가 아닌 링크에는 `target="_blank"`가 없는지. 판단에는 `src/lib/`의 같은 함수를 쓴다.
  - 표시가 있는지는 화면 낭독기 문구가 그 페이지 언어(`<html lang>`)의 사전 문구와 같은지까지 본다(예: 영어 페이지에 "(새 탭에서 열림)"이 나오지 않는지). md 플러그인은 언어를 페이지가 아니라 글 파일 이름으로 따로 정하므로 어긋날 수 있는 곳이기 때문이다(2026-10-21 검토에서 나왔다). 하위 단계 2에서 정한 방식: 컴포넌트와 플러그인이 만드는 마크업이 같으므로(링크 글자 span, U+2060, 화면 낭독기 이름을 가진 아이콘 span), 링크 안의 마크업이 그 페이지 언어의 문구를 넣은 이 구조와 글자 그대로 같은지 본다.
- 이 검사가 있으면 누군가 컴포넌트를 쓰지 않고 `<a>`를 직접 쓴 외부 링크도 빌드에서 잡힌다. 공통 코드를 쓰도록 강제하는 장치다.

## 결정

2026-10-21 사용자가 모두 추천안으로 확정했다.

- `rel` 값: `noopener`만 붙인다(`noreferrer`는 붙이지 않는다). 이유는 [붙는 속성](#붙는-속성).
- 링크 컴포넌트 범위: 외부 링크 전용이 아니라 모든 링크를 받는 컴포넌트로 만든다. 이유는 [공통화](#공통화).
- md 플러그인: `rehype-external-links` 패키지를 쓰지 않고 직접 만든다. 이유는 [공통화](#공통화).

   - 표시 3안: A 고정폭 글자 기호 `↗`(링크와 같은 색·크기), B 작은 SVG 아이콘(상자에서 나가는 화살표, 링크와 같은 색), C `↗`를 작게(`text-xs`) 흐린 글자색으로(마우스를 올리면 링크의 hover 색).
   - 카드 링크 처리 2안: 앞 기호 `→`를 두고 뒤에 표시를 더하기 / 외부 링크만 앞 기호를 `↗`로 바꾸기(뒤 표시 없음).
   - 시안을 만들며 정한 구현 조건(어느 안이든 같다):
     - 표시는 링크 글자 바로 뒤에 줄바꿈하지 않는 글자(U+2060)를 두고 붙인다. 링크가 줄바꿈될 때 표시만 다음 줄로 떨어지지 않게 하기 위해서다.
     - 표시는 `inline-block`이 아니라 일반 인라인 요소로 만든다. 처음 시안에서 `inline-block`으로 했더니 U+2060이 있어도 표시만 다음 줄로 떨어졌다(브라우저는 inline-block 앞을 줄바꿈 가능한 곳으로 본다). 아이콘(B안)도 빈 인라인 요소에 가로 안쪽 여백으로 폭을 주고 글자색 배경을 아이콘 모양으로 오려 낸다(`mask`).
     - 글 본문 링크의 밑줄은 링크 글자에만 긋는다(링크 글자를 span으로 감싼다). 링크 전체에 그으면 인라인인 표시까지 밑줄이 이어진다. 그래서 링크 컴포넌트와 md 플러그인은 같은 구조(링크 글자 span, U+2060, 표시)를 만든다. 화면 낭독기 문구는 하위 단계 2 뒤 검토에서 표시(아이콘)의 이름으로 옮겼다([표시](#표시)).
   - 확인: 세 안·두 카드 처리·두 언어 모두 모바일(375px)에서 가로 스크롤이 없고, 줄바꿈되는 긴 링크에서 표시가 앞 글자와 같은 줄에 남는다. 영어 화면 본문에 한글이 없다.
   - 할 일: 외부 링크 표시를 HTML 시안으로 만든다(`docs/changes/2-external-links/`). 기준 시안 [c-mono.html](../stages/3-ui-design/c-mono.html)과 design.md 공통 UI의 디자인 값만 쓴다. 두세 안(예: 글자 기호 `↗`, 작은 SVG 아이콘, 크기·색 차이)을 링크가 나오는 모든 곳에서 보여 준다.
     - 포트폴리오 카드 링크(앞 기호 `→`가 있다), 소개 페이지 링크, 푸터 링크(흐린 글자색), 글 본문 링크(밑줄), 한 줄에 다 들어가지 않아 줄바꿈되는 긴 링크
     - 한국어·영어 화면, 데스크톱과 모바일(375px)
   - 완료 확인: 사용자가 한 안을 승인하고, 승인한 모양을 이 문서의 [표시](#표시)에 적는다.

## 위험과 한계

- 새 탭을 원하지 않는 방문자도 있다: 외부 링크는 항상 새 탭으로 열려, 현재 탭에서 열고 싶은 사람은 그렇게 할 방법이 없다(새 탭 → 현재 탭으로 바꾸는 단축키는 없다). 대신 표시가 있어 누르기 전에 알 수 있다.
- md 본문에 HTML로 직접 쓴 `<a>`(마크다운 문법이 아닌 것)는 플러그인이 처리하지 못한다(처리기가 element가 아니라 raw HTML로 둔다. 구현 때 확인). 빌드 결과 검사가 잡아 배포되지 않으므로, 글에서는 마크다운 링크 문법을 쓴다(design.md 코드 규칙).
- Astro를 올릴 때 `@astrojs/markdown-satteri`의 고정 버전도 Astro가 쓰는 버전에 맞춰야 한다. 맞추지 않으면 처리기가 두 벌 설치된다.

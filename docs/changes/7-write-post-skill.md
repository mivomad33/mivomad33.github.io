# 변경 7: 대화로 글을 기획해 쓰고 배포하는 스킬(write-post)

- 상태: 완료(2026-10-25). 스킬은 사용자 검토를 통과해 main에 squash merge했고, 첫 실제 글로 시험 실행을 마쳤다.
- 브랜치: `change/7-write-post-skill`

## 배경

- [변경 6](6-add-project-skill.md)의 `add-project`는 완성한 프로젝트를 재료로 글을 쓴다. 프로젝트와 관계없는 일반 글(생각, 경험, 배운 것)을 쓸 방법은 따로 없었다.
- 사용자가 초기 아이디어만 넘기면 AI가 방향을 제안하고 질문을 주고받으며 글을 구체화하고, 초안을 개발 서버로 보여 주고 고친 뒤, 승인하면 push·배포까지 하는 스킬을 만들자고 했다(2026-10-25).
- 명세서(`write-spec`)는 쓰지 않는다. 변경 6과 같은 이유다(한 세션에서 끝낼 크기이고, 스킬 파일이 곧 지침 문서이며, 품질은 실제로 돌려 봐야 확인된다).

## 요구사항

### 해야 하는 것

- 이 저장소에서 `/write-post <아이디어>`로 부르면, 대화로 글을 기획하고 글 폴더(`src/content/blog/<slug>/`의 `ko.md`, `en.md`, 필요하면 `images/`)를 만들어 main에 push하고 배포까지 확인한다. 아이디어가 없으면 묻는다.
- 아이디어를 분석해 좋은 글이 될 방향을 제안하고, 질문을 주고받으며 구체화한다.
- 기획이 충분해지면 그렇다고 알리고, 사용자가 확인한 뒤에야 초안을 쓴다.
- 초안은 개발 서버로 보여 주고, 사용자가 승인할 때까지 고친다.
- 글의 사실(경험, 사례, 숫자)은 대화에서 사용자가 말한 것만 쓴다.

### 하지 않는 것

- 포트폴리오 항목은 다루지 않는다(`add-project`의 일이다).
- 화면 모양을 바꾸지 않으므로 시안 단계를 두지 않는다.
- 이미지는 Claude가 만들거나 찍지 않는다. 필요하면 사용자가 파일을 준다.

## 설계

### 흐름

**아이디어 받기 → 방향 제안과 질문(반복) → "쓸 준비가 됐다" 알림 → 사용자 확인 → 한국어 초안을 개발 서버로 보이기 → 수정(반복) → 한국어 승인 → 영어 글 → 영어 확인 → 검증 → push 승인 → push → 배포 확인 → 보고**

사용자 확인을 받는 곳은 네 곳이다: 쓰기 시작, 한국어 승인, 영어 확인, push. push는 되돌리기 어려운 공개 작업이라 따로 확인받는다.

### 기획 대화

- 처음에 아이디어를 분석해 다음을 보인다: 이 아이디어로 쓸 수 있는 글의 방향 2~3개(추천안을 앞에 두고 이유를 짧게), 그리고 첫 질문.
- 질문은 한 번에 1~3개만 한다. 고를 수 있는 질문은 선택지를 주고 추천안을 앞에 둔다. 경험을 묻는 질문은 "그때 실제로 무엇을 했나요?", "무엇이 예상과 달랐나요?"처럼 구체적인 장면·숫자·실패를 끌어내게 한다. 일반론은 누구나 쓸 수 있어 글의 가치가 되지 않고, AI가 빈 곳을 일반론으로 메우는 것이 이런 글의 가장 흔한 실패이기 때문이다.
- 매 회차 끝에 **기획 체크리스트**를 보인다. 항목마다 정해진 내용 또는 "아직"을 적는다.
  - 중심 메시지 한 줄(독자가 가져갈 것)
  - 대상 독자
  - 섹션 구성안
  - 섹션마다 쓸 구체적인 재료(사용자가 말한 경험·사례·숫자)
  - 제목(한국어)과 slug, 설명(한두 문장)
- 모든 항목이 채워지면 "쓸 준비가 됐다"고 알리고 기획안 전체를 보인다. 사용자가 확인해야 쓰기 시작한다. 사용자가 더 일찍 "이걸로 써 줘"라고 하면 빈 항목을 알리고 그래도 쓰는지 확인한 뒤 쓴다.
- 대화에서 나온 사실은 **기획 메모**에 모은다(사용자가 한 말, 정한 것). 쓰기 단계에서는 이 메모에 있는 사실만 쓴다(`add-project`의 사실 메모와 같은 원칙).

### 기획 메모의 위치

- `drafts/<날짜>-<임시 이름>.md`(저장소 루트, `.gitignore`에 넣는다). 대화가 길어 세션이 끊겨도 다음 세션에서 이어 가기 위해서다. 세션 임시 폴더는 세션이 바뀌면 찾을 수 없고, 글 폴더에는 정해진 파일만 둘 수 있어(블로그 로더가 빌드를 멈춘다) 둘 다 쓰지 않는다.
- 스킬을 부를 때 `drafts/`에 메모가 있으면 이어 갈지 묻는다. push와 배포 확인이 끝나면 메모를 지운다.

### 초안과 영어 글(2026-10-25, 추천안·사용자 승인)

- 한국어를 먼저 다듬고, 승인받은 뒤 영어를 쓴다. 수정할 때마다 두 언어를 같이 고치면 일이 두 배가 되고 둘이 어긋나기 쉽기 때문이다. 뺀 안: 처음부터 두 언어를 함께 쓰기.
- 블로그 로더는 `en.md`가 없으면 오류를 내므로, 한국어 초안 동안에는 영어 임시 파일(`title`·`description`은 `Draft`, `date`는 한국어와 같게, 본문 한 줄)을 둔다. 임시 파일은 커밋하지 않는다. 커밋 전 검증에서 영어 글이 임시 상태가 아닌지 확인한다.
- 초안은 개발 서버(`.claude/launch.json`의 `site-dev`)를 내장 브라우저로 열어 보여 주고, 사용자는 같은 창에서 읽는다. 고친 뒤에는 새로 고침으로 다시 보인다.

### 공통 글쓰기 규칙(2026-10-25, 추천안·사용자 승인)

- `add-project`의 글쓰기 규칙(형식, 내용 원칙, 문체, 영어 글)과 검증·커밋 규칙 가운데 글에 관한 것을 `.claude/skills/shared/post-writing.md` 한 파일로 옮기고, 두 스킬이 이 파일을 참조한다. 같은 규칙을 두 스킬에 두면 고칠 때 어긋나기 때문이다(`CLAUDE.md`의 공통 코드 규칙과 같은 이유). 뺀 안: `docs/`의 새 문서(문서 역할 목록에 새 종류를 더해야 하고, Claude가 따르는 지침이라 스킬 옆이 맞다), 스킬마다 따로 두기.
- `shared/`에는 `SKILL.md`가 없어 스킬로 잡히지 않는다.
- 사실의 출처만 두 스킬이 다르다: `add-project`는 원본 프로젝트의 문서·코드, `write-post`는 사용자와의 대화. 공통 파일은 "사실 메모에 있는 것만 쓴다"로 적고, 메모를 만드는 방법은 각 스킬에 둔다.
- 만들면서 정한 것: 아래 push와 배포 규칙도 공통 파일에 두어 `add-project`도 따른다. 그래서 `add-project`는 보고 뒤 push 확인을 받아 main에 push하고 배포까지 확인하는 것으로 바뀌었다(전에는 8단계 완료 전이라 작업 브랜치에 커밋하고 머지를 기다렸다). 8단계 완료 전이라도 실제 콘텐츠는 main에 push한다는 당시 결정(2026-10-25, memory.md에 있었고 8단계를 마쳐 지웠다)과 맞추기 위해서다.

### push와 배포

- 커밋은 `CLAUDE.md`의 콘텐츠 예외를 따른다: 글 폴더만 바꾼 커밋을 main에 바로 push한다. 다른 파일이 섞이면 예외가 아니므로 멈추고 알린다.
- push 전에 커밋할 파일 목록과 글 주소를 보이고 확인받는다. `pre-push` 훅의 검사를 건너뛰지 않는다.
- push 뒤 그 커밋의 GitHub Actions 실행(`gh run watch`)이 끝나기를 기다리고, 운영 주소의 두 언어 글(`https://mivomad33.dev/blog/<slug>/`, `/en/blog/<slug>/`)이 200으로 열리는지 본다. 실패하면 원인을 알리고 고칠 방법을 제안한다.

### 정한 것(2026-10-25, 모두 추천안·사용자 승인)

- 이름: `write-post`. 뺀 안: `new-post`(대화로 기획하는 과정이 드러나지 않는다), `draft-post`(push·배포까지 하는 범위보다 좁아 보인다).
- 위치: 이 저장소의 `.claude/skills/write-post/`. `add-project`와 같은 이유다(이 블로그의 글 형식에 묶여 있다).
- 시험 실행: 확인용 글은 넣지 않으므로(사용자 결정, [8단계 문서](../stages/8-launch.md#하위-단계-4-공개와-검색-엔진-등록)), 사용자의 실제 다음 글로 처음 돌린다. 그 글을 main에 push하는 것으로 8단계의 운영 흐름 확인도 함께 끝낸다. 스킬은 먼저 작업 브랜치에서 검토받아 main에 머지한다.

   - 흐름: 기획 대화 4회(첫 응답과 방향·독자 선택, 경험 질문 두 번, 비공개 사실·스킬 공개 범위 선택) 뒤 "쓸 준비" 알림과 제목 선택, 한국어 초안 한 번에 승인, 영어 글 한 번에 확인, 검증, push 확인, 배포 확인. 확인 지점 네 곳을 모두 거쳤다.
   - 잘된 것:
     - 경험 질문에서 일반적인 첫 답("구현이 제대로 안 됐다", "빠르다")을 한 번 더 구체적으로 물어 "지침 누락과 재수정", "하루 대 며칠"이라는 재료를 얻었다.
     - 사용자 답 외에 사용자가 가리킨 파일(스킬 파일, 다른 프로젝트의 명세서 목록)에서 사실을 출처와 함께 메모에 모았고, 다른 프로젝트의 `docs/specs`가 git에 없어 비공개라는 것을 찾아 공개 범위를 물었다.
     - 사실 대조에서 근거 없는 표현 세 곳(사용자가 말하지 않은 "효과가 컸던 규칙" 등)을 잡아 고쳤다.
     - 영어 임시 파일 방식으로 한국어 초안을 개발 서버에 띄우는 데 문제가 없었다.
   - 스킬에 반영할 것: 없음. 다음 두 가지는 이번에 문제가 되지 않아 스킬을 고치지 않고 적어만 둔다.
     - 내장 브라우저 창이 좁으면 데스크톱 폭 화면을 확인할 수 없다. 이번에는 기존 글과 같은 레이아웃이라 375px 확인과 스크린샷으로 대신했다.
     - 배포 확인의 `gh run watch` 출력에 저장소 이름이 없어, 실행 결과를 `gh run view --repo`로 다시 확인했다.
   - 글은 콘텐츠 예외로 main에 push하고, 배포 확인까지 마치면 8단계를 완료로 표시한다([8단계 문서](../stages/8-launch.md), [plan.md](../plan.md)).
   - 시험에서 나온 고칠 점은 작업 브랜치에서 스킬에 반영하고 여기에 적는다.

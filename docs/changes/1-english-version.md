# 변경 1: 영어 버전 추가(한국어·영어 두 언어)

- 상태: 기획·설계 확정(2026-10-21, 사용자가 추천안으로 확정). 확인하지 못했던 두 가지(라우팅 방식, `prepare` 실행)는 구현 전에 확인했다([확인 결과](#구현-전-확인-결과2026-10-21)). 완료(2026-10-21). 하위 단계 1~5를 모두 마쳤고, 변경 전체가 사용자 검토를 통과해 main에 squash merge했다.
- 브랜치: `change/i18n`

## 배경

- 지금 사이트는 한국어로만 만들어져 있다(개요의 원칙 "사이트 언어는 한국어만 사용한다", design.md 코드 규칙 "다국어 처리 없음").
- 사용자는 영어로도 서비스해, 영어로 검색하는 사람에게는 영어 페이지가, 한국어로 검색하는 사람에게는 한국어 페이지가 나오기를 원한다(2026-10-21 사용자 요청). 대상(채용 담당자, 사업 파트너, 개발자 독자)이 한국어 사용자에 한정되지 않기 때문이다.
- 영어 글은 사용자가 직접 쓰지 않고, 한국어로 쓴 뒤 AI로 번역해 넣는다.
- 시점: 공개(8단계 하위 단계 4) 전이고 글·포트폴리오가 하나도 없다. 공개 뒤에 URL 구조를 바꾸면 검색 엔진에 등록된 주소를 옮겨야 하고 기존 콘텐츠도 옮겨야 하므로, 지금 하는 것이 가장 비용이 적다.

## 요구사항

### 해야 하는 것

- 모든 페이지(홈, 포트폴리오, 블로그 목록, 글 보기, 소개)를 한국어와 영어 두 버전으로 제공한다.
- 두 버전은 별개의 사이트가 아니다. 콘텐츠 하나(글 하나, 포트폴리오 항목 하나)를 한 곳에서 관리하고, 그 안에 한국어와 영어 버전이 함께 있다.
- 헤더에 언어 전환 링크를 하나 둔다. 누르면 지금 보고 있는 페이지의 다른 언어 버전으로 간다. 콘텐츠마다 따로 두지 않는다.
- 검색 엔진이 두 버전을 같은 페이지의 언어별 버전으로 알아보게 해, 검색한 언어에 맞는 버전이 나오게 한다.
- 블로그 글과 포트폴리오(프로필 포함)에 한국어와 영어 버전이 모두 있지 않으면 배포되지 않는다. push도 로컬에서 막는다(아래 [두 언어 강제](#두-언어-강제)).

### 하지 않는 것

- 브라우저 언어나 지난번에 고른 언어를 보고 자동으로 다른 언어로 이동시키지 않는다(이유는 [URL과 언어](#url과-언어)).
- 번역 자동화(번역 스크립트, API 연동)는 넣지 않는다. 사용자가 AI로 번역한 결과를 파일에 넣는다.
- 두 언어의 내용이 서로 맞는지(번역이 최신인지)는 검사하지 않는다. 있는지만 검사한다(한계는 [위험과 한계](#위험과-한계)).
- 한국어·영어 밖의 언어는 지금 넣지 않는다. 다만 언어 목록을 한 곳에 두어, 나중에 늘릴 때 그 목록과 콘텐츠만 늘리면 되게 한다.

## 설계

### URL과 언어

- 한국어는 지금 주소 그대로(`/`, `/portfolio/`, `/blog/`, `/blog/<slug>/`, `/about/`), 영어는 앞에 `/en`을 붙인다(`/en/`, `/en/portfolio/`, `/en/blog/<slug>/`, `/en/about/`).
  - 이유: 한국어가 원문이고, 지금 정한 주소 규칙(design.md 페이지 구성)을 바꾸지 않는다. 두 언어 모두 접두어를 붙이면(`/ko/`, `/en/`) 루트(`/`)에서 어느 언어로 보낼지 정해야 하는데, 정적 사이트(GitHub Pages)는 서버에서 언어별로 보낼 수 없어 루트가 빈 이동 페이지가 된다.
- 글의 slug는 두 언어가 같다(이미 영문 소문자 규칙이라 그대로 쓸 수 있다).
- 언어 코드: `ko`, `en`. `<html lang>`, `hreflang`에 이 값을 쓰고, `og:locale`은 `ko_KR`, `en_US`이다.
- 언어 목록과 기본 언어(`ko`), 언어별 경로를 만드는 함수는 `src/lib/i18n.ts` 한 곳에 둔다. 페이지와 컴포넌트는 주소를 직접 조합하지 않고 이 함수를 쓴다(내부 링크에 `/en`을 빠뜨리는 실수를 막기 위해서다).
- 자동 이동은 하지 않는다.
  - 구글 크롤러는 주로 미국에서 언어 설정 없이 접속하므로, 언어를 보고 이동시키면 한국어 페이지를 보지 못해 색인에서 빠질 수 있다(구글도 언어별 페이지에 자동 이동을 권하지 않는다).
  - 정적 사이트에서 이동하려면 클라이언트 JS가 필요한데, 코드 규칙은 클라이언트 JS를 쓰지 않는 것이 기본이다.
  - 주소 자체가 언어를 나타내므로, 고른 언어를 기억할 필요가 없다.

### 언어 전환 링크

- 위치: 헤더의 메뉴 오른쪽 끝. 모든 페이지에 있다(404 제외, 아래 [404](#404)).
- 동작: 지금 페이지의 다른 언어 버전 주소로 가는 일반 링크(`<a>`)다. `/blog/abc/`에서는 `/en/blog/abc/`로, `/en/about/`에서는 `/about/`으로 간다. 모든 페이지가 두 언어로 있으므로 이동할 곳이 없는 경우는 없다.
  - 일반 링크인 이유: 크롤러가 따라가 두 버전을 연결된 페이지로 이해하는 데 도움이 되고, JS 없이 동작한다.
- 모양(하위 단계 1의 시안 B1안, 2026-10-21 사용자 결정): 두 언어 코드를 `ko/en`처럼 고정폭(`font-mono`, `text-sm`)으로 붙여 쓰고(사이 간격 `--spacing`의 0.5배), 전체가 링크 하나다. 지금 언어는 강조색 굵게, 다른 언어와 `/`는 흐린 글자색이고, 마우스를 올리면 다른 언어와 `/`가 본문 글자색이 된다(시안과 같다). 테두리는 두지 않는다. 메뉴 뒤에 메뉴 사이 간격(`--spacing`의 4배)을 두고 놓으며, 좁은 화면에서는 메뉴와 함께 사이트 이름 아래 줄로 내려간다. design.md 공통 UI에는 하위 단계 3에서 적는다.
  - 지금 언어를 보여 주고 눌러서 바꾸는 방식이다. 처음 안(이동할 언어 이름 `English`만 보여 주기)은 그 이름이 지금 언어처럼 읽혀 헷갈려서 바꿨다. 언어가 둘뿐이라 어디를 눌러도 다른 언어로 가는 링크 하나로 묶었다. 테두리를 두른 안(B2)도 비교했지만, 헤더의 다른 요소처럼 상자 없이 두는 B1을 골랐다.
  - 화면 낭독기: 링크에 이동할 언어 이름을 `aria-label`로 붙이고(`English`/`한국어`), `hreflang`과 `lang`도 그 언어로 붙인다. 화면의 `ko/en`보다 무엇을 하는 링크인지 분명하기 때문이다.
  - 국기는 국가를 나타내지 언어를 나타내지 않으므로 쓰지 않는다.

### 콘텐츠 형식

공통 규칙:

- 언어마다 달라야 하는 글자(소개, 설명, 제목 등)는 `ko`와 `en`을 모두 적어야 한다. 하나라도 빠지거나 비면 빌드가 실패한다.
- 언어와 관계없는 값(활동명, 이메일, 링크 주소, 날짜)은 한 번만 적는다(같은 값을 두 번 적다가 어긋나지 않게 하기 위해서다).
- 영어 값에는 한글이 들어갈 수 없다(빌드 실패). 한국어를 그대로 복사해 넣고 번역을 잊는 실수를 잡기 위해서다. 글 본문에는 적용하지 않는다(영어 글에서 한국어 낱말을 소개할 수 있으므로).
- 링크명(`label`)과 포트폴리오 명칭(`name`)은 고유명사가 많아(GitHub, 프로젝트 이름) 두 언어가 같은 경우가 대부분이다. 그래서 한 값만 적을 수도 있고(두 언어가 같이 쓴다), `ko`·`en`으로 나눠 적을 수도 있다. 한 값만 적을 때는 한글이 들어갈 수 없다(영어 페이지에 한글이 나오지 않게 하기 위해서다).

프로필(`src/data/profile.yaml`):

```yaml
name: mivomad33
intro:
  ko: 1인 사업가를 꿈꾸는 개발자
  en: A developer who dreams of becoming a solo entrepreneur
email: mivomad33@gmail.com
links:
  - label: GitHub
    url: https://github.com/mivomad33
```

- `name`: 활동명. 한 값(두 언어가 같다).
- `intro`: `ko`, `en` 필수.
- `links[].label`: 한 값(한글 불가) 또는 `ko`·`en`.

포트폴리오(`src/data/portfolio.yaml`):

```yaml
- name: miv-profile-blog
  description:
    ko: 프로필, 포트폴리오, 블로그를 담은 개인 사이트
    en: A personal site with my profile, portfolio, and blog
  links:
    - label:
        ko: 사이트
        en: Site
      url: https://mivomad33.dev
```

- `name`: 한 값(한글 불가) 또는 `ko`·`en`.
- `description`: `ko`, `en` 필수.
- `links`: 프로필과 같다.

블로그 글: 글마다 폴더 하나에 언어별 파일을 둔다.

```text
src/content/blog/
  first-post/
    ko.md
    en.md
    images/        (선택)
      layout.png
```

- 폴더 이름이 slug다(규칙은 지금과 같다). 폴더 안에는 `ko.md`, `en.md`가 반드시 둘 다 있어야 하고, 그 밖에는 `images/` 폴더만 둘 수 있다. 하나가 빠지거나 다른 파일이 있으면 빌드가 실패한다.
- 두 파일의 frontmatter 필드는 지금과 같다(`title`, `description`, `date`, `updated`). `date`와 `updated`는 두 파일이 같아야 한다(다르면 빌드 실패).
  - 날짜를 한 파일에만 적게 하는 방법도 있지만, 파일마다 형식이 같으면 규칙이 단순하고 AI 번역 때 frontmatter를 그대로 옮기면 된다. 또 한국어 글을 크게 고쳐 `updated`를 바꾸면 영어 글의 `updated`도 바꿔야 빌드가 통과하므로, 영어 글을 다시 번역할 계기가 된다.
- 이미지: 글 폴더의 `images/`에 두고 두 언어가 같이 쓴다. 본문에서 `./images/layout.png`처럼 넣고, 대체 텍스트는 언어마다 그 언어로 쓴다.
  - 6단계에서는 이미지가 없는 글이 대부분이면 글이 파일 하나로 남는 방식이 낫다고 보고 `images/<slug>/`를 따로 두었다([6단계 문서](../stages/6-blog.md#이미지)). 이제 모든 글이 파일 두 개라 글마다 폴더가 생기므로, 이미지도 그 폴더에 두는 편이 단순하다. 글이 아직 없어 옮길 것도 없다.
- 로더: 언어 파일마다 항목 하나를 만든다(id `<slug>/<언어>`). 파일 검사(폴더 구조, 짝, 날짜 일치)는 지금처럼 `blogLoader`가 읽기 전에 한다. 블로그 스키마는 하나라 언어를 모르므로, `en.md`의 `title`·`description`에 한글이 있는지도 로더가 파일 이름으로 언어를 알아 검사한다.
- 글을 가져오는 함수: 글 목록·이전·다음 글을 가져오는 함수는 언어를 받고, 글마다 `slug`를 따로 돌려준다. 컴포넌트와 페이지는 주소를 만들 때 id가 아니라 이 `slug`를 쓴다. 지금은 id를 주소에 바로 쓰는데(`PostListItem.astro`, `blog/[slug].astro`), id가 `<slug>/ko`가 되면 `/blog/<slug>/ko/` 같은 주소가 생기기 때문이다. 두 언어의 날짜가 같으므로 정렬 순서와 이전·다음 글도 두 언어가 같다.

### 두 언어 강제

막는 곳은 세 겹이다.

- 빌드(핵심): 위 콘텐츠 형식의 검사가 스키마와 로더에서 빌드를 실패시킨다. CI의 빌드가 실패하면 배포 작업이 실행되지 않으므로(4단계의 `needs`), 한 언어만 있는 콘텐츠는 배포되지 않는다. 콘텐츠를 main에 바로 push하는 경우(공개 뒤, [6단계 문서](../stages/6-blog.md#하위-단계-3-공개-뒤-콘텐츠-반영-방식))에도 같다.
- 빌드 결과 검사: 한국어 페이지마다 영어 페이지가 있고 그 반대도 있는지, 언어 표시(`lang`, `hreflang`, `og:locale`)가 맞는지 확인한다(아래 [SEO](#seo)). 콘텐츠 검사를 빠져나간 경우나 페이지 코드의 실수를 잡는다.
- push(보조): 로컬 Git `pre-push` 훅이 `pnpm verify`를 실행해, 실패하면 push를 멈춘다. `pnpm install` 때 연결된다. 연결 방법과 동작, 건너뛰는 경우는 [design.md 테스트 전략](../design.md#테스트-전략)이 기준이다(같은 내용을 두 곳에 두지 않기 위해 여기에는 결정과 이유만 둔다).
  - 훅은 보조 장치다. `git push --no-verify`로 건너뛸 수 있고 GitHub 웹에서 고치면 실행되지 않으므로, 실제로 배포를 막는 것은 빌드다.
  - GitHub 브랜치 보호(상태 검사 필수)로 push 자체를 서버에서 막는 방법은 쓰지 않는다. 필수 검사를 켜면 main에 직접 push하는 커밋도 다른 브랜치에서 검사를 먼저 통과해야 받아들여진다. 그러면 콘텐츠를 main에 바로 push하는 결정(6단계)이 "브랜치에 올려 검사를 기다린 뒤 main에 push"로 바뀌어, 절차를 가볍게 하려던 이유가 사라진다.

### 화면 문구

- 코드에 쓰는 화면 문구(메뉴, "전체 보기", "이전 글", "수정", 빈 목록 안내, 페이지 제목, 목록 페이지 설명, 화면 낭독기용 `aria-label` 등)는 `src/lib/i18n.ts`의 언어별 사전 하나에 모은다.
- 한국어 사전의 키를 기준으로 영어 사전의 타입을 정해, 영어 문구가 하나라도 빠지면 타입 검사(`pnpm check`)가 실패하게 한다.
- 영어 문구: 하위 단계 1의 시안에서 승인한 문구를 쓴다(2026-10-21 승인). 전체 목록은 시안의 "영어 문구" 화면(`mockup.js`의 `strings`)에 있고, 하위 단계 3에서 사전으로 옮긴 뒤로는 사전이 기준이다. "최근 포트폴리오"는 직역("Recent portfolio")이 어색해 "Recent projects"로 쓴다.
- 날짜 형식(`YYYY-MM-DD`)은 언어와 관계없으므로 그대로 쓴다. 수정일 앞의 "수정"만 영어에서 "Updated"가 된다.
- 글꼴: 영어 문장도 `font-sans`(Pretendard에 라틴 글자가 있다)로 쓴다. `font-mono`는 지금처럼 기호·날짜·사이트 이름·코드에만 쓴다. 한글 줄바꿈 규칙(`keep-all`)은 영어에도 문제가 없다.

### 페이지 구현 방식

- 페이지 파일은 언어마다 따로 만들지 않는다. 페이지마다 파일 하나가 언어 매개변수로 두 언어 페이지를 모두 만든다(`src/pages/[...locale]/` 아래에 두고 `getStaticPaths`가 `ko`는 접두어 없이, `en`은 `/en`으로 만든다). 같은 화면을 두 파일로 두면 한쪽만 고치는 실수가 생기기 때문이다.
  - Astro 내장 i18n 라우팅은 쓰지 않는다. 내장 방식은 언어마다 `src/pages/en/` 같은 폴더에 페이지를 따로 두는 것을 전제로 하기 때문이다.
  - 나머지 매개변수를 경로 중간에 두는 것(예: `[...locale]/blog/[slug].astro`)이 Astro 7.4에서 되는 것을 확인했다([확인 결과](#구현-전-확인-결과2026-10-21)).
- `BaseLayout`은 언어를 받아 `<html lang>`, 메타 태그, 헤더 메뉴·언어 전환 링크, 푸터를 그 언어로 만든다.
- 404와 `robots.txt`는 언어별로 만들지 않는다(사이트에 하나씩이다).

### SEO

- 페이지마다(404 제외) `<link rel="alternate" hreflang="...">`로 두 언어 버전을 서로 알린다. `ko`, `en`, `x-default` 세 개이고, 자기 자신도 포함한다.
  - `x-default`는 영어 페이지다. 한국어도 영어도 아닌 언어로 검색한 사람에게는 영어가 더 읽기 쉽기 때문이다.
  - `href`는 canonical처럼 사이트 주소(`SITE`) 기준 절대 주소다(`siteUrl()`로 만든다).
- canonical과 `og:url`은 지금처럼 자기 주소다(영어 페이지의 canonical이 한국어 페이지를 가리키면 영어 페이지가 색인에서 빠진다).
- `og:locale`은 페이지 언어(`ko_KR`/`en_US`)이고, 다른 언어는 `og:locale:alternate`로 넣는다.
- 구조화 데이터(`BlogPosting`)에 `inLanguage`를 넣는다. 작성자 주소(`author.url`, 지금은 `/about/`로 고정)는 그 언어의 소개 페이지(영어 글은 `/en/about/`)다.
- OG 이미지 대체 텍스트(`og:image:alt`, `<활동명> - <한 줄 소개>`)는 그 언어의 한 줄 소개를 쓴다.
- 제목 형식(`<제목> - <활동명>`)과 설명 출처 규칙은 그대로이고, 값만 그 언어의 것을 쓴다(목록 페이지의 고정 설명은 화면 문구 사전에서).
- sitemap: `@astrojs/sitemap`의 `i18n` 설정으로 두 언어 주소를 모두 넣고, 주소마다 다른 언어 버전(`xhtml:link`)을 붙인다.
  - 이 설정은 `ko`·`en` 링크만 붙이고 `x-default`는 붙이지 않는다. `x-default`는 페이지의 `hreflang` 링크로만 알린다(두 방법이 서로 다른 말을 하지 않으면 함께 써도 된다).
  - 다른 언어 버전이 없는 주소에는 링크를 붙이지 않고 조용히 넘어간다. 그래서 빌드 결과 검사가 모든 주소에 링크가 있는지 확인한다.
- OG 이미지: 언어마다 하나씩 둔다(`public/og.png`, `public/og-en.png`). 지금 이미지에 한국어 한 줄 소개가 글자로 들어 있어, 영어 페이지를 공유하면 한국어가 보이기 때문이다. 영어 이미지는 지금 이미지와 같은 모양에 한 줄 소개만 영어로 바꾼다(하위 단계 1의 시안 [og-image-en.html](1-english-version/og-image-en.html), 2026-10-21 승인. 소개가 길어 두 줄이 된다). 원본 HTML과 `make-images.sh`가 두 이미지를 만들고, 빌드 결과 검사는 언어별 원본의 한 줄 소개가 프로필의 그 언어 값과 같은지 본다.
- 빌드 결과 검사(`scripts/check-build.ts`)에 더할 것:
  - 한국어 페이지 경로마다 `/en` 페이지가 있고, 그 반대도 있는지
  - 페이지마다 `<html lang>`과 `og:locale`이 경로의 언어와 맞고, `og:locale:alternate`가 있는지
  - `hreflang` 링크 세 개가 있고, 실제 있는 페이지를 가리키며, 서로를 가리키는지
  - 언어 전환 링크가 다른 언어 버전을 가리키는지
  - 글 보기 페이지가 글 폴더마다 두 언어로 있는지
  - sitemap에 모든 페이지의 두 언어 주소가 있고, 주소마다 다른 언어 버전이 붙어 있는지
- 검색 엔진 등록(공개 때)은 그대로 8단계 하위 단계 4에서 한다. sitemap 하나에 두 언어가 들어 있으므로 따로 등록할 것은 없다.

### 404

- GitHub Pages는 없는 주소에 사이트 루트의 `404.html` 하나만 보여 주므로, 404는 하나로 두고 한국어와 영어를 함께 쓴다.
- 모양(하위 단계 1의 시안, 2026-10-21 승인): 페이지 제목 "페이지를 찾을 수 없습니다" 아래에 "Page not found"(`text-xl`, 흐린 글자색, 소개 페이지의 한 줄 소개처럼 제목에 붙인다), 그 아래 한 줄에 "홈으로 가기"(`/`)와 "Go to home"(`/en/`) 링크를 나란히 둔다(강조색, 마우스를 올리면 밑줄).
  - 홈 링크를 둘 다 두는 것은 영어를 못 알아들어서가 아니라 가는 곳이 달라서다. 방문자가 어느 언어 페이지에서 왔는지 알 수 없으므로, 두 링크로 자기 언어의 홈에 한 번에 가게 한다(사용자 확인).
- `<html lang="ko">`로 두고 영어 부분에 `lang="en"`을 붙인다. 언어 전환 링크는 두지 않는다(두 언어가 이미 다 보이고, 이동할 다른 언어 버전이 없다). 헤더 메뉴와 푸터는 한국어로 둔다.

## 위험과 한계

- 번역이 낡을 수 있다: 한국어 본문만 고치고 영어를 그대로 두는 것은 막지 못한다. `updated`를 바꾸면 영어도 바꿔야 해 큰 수정은 어느 정도 잡히지만, 작은 수정은 사용자가 챙긴다. 자주 문제가 되면 그때 다른 방법(예: 두 파일의 수정 시점 비교)을 정한다.
- 글 쓰는 부담: 글 하나가 파일 두 개가 되고, 영어 번역 없이 한국어만 먼저 올릴 수 없다. 사용자가 요구한 동작이다.
- AI 번역 품질: 구글이 문제 삼는 것은 대량으로 찍어 낸 가치 없는 콘텐츠이고, 원문이 있는 번역은 해당하지 않는다. 다만 영어 독자에게 어색하지 않게 사용자가 결과를 한 번 훑어보는 것을 권한다.
- 페이지 수가 두 배가 되어 빌드 시간이 조금 늘고, pre-push 훅이 push마다 전체 검증을 돌려 push가 그만큼 느려진다(지금 사이트 크기에서는 문제가 되지 않는다).

# 3단계: UI 디자인 시안

목적, 끝난 상태, 하위 단계는 [진행 계획](../plan.md)의 3단계를 따른다. 이 문서는 시안의 콘셉트와 비교, 결정 이유를 담고, 확정된 값은 [design.md](../design.md#공통-ui)의 공통 UI에 적는다.

- 상태: 완료(2026-10-20, 사용자 검토 통과)

## 시안 보는 방법

- 시안 파일은 [3-ui-design/](3-ui-design/)에 있다. 시안 A·B·C 각각 HTML 파일 하나이고, `index.html`은 시안 목록이다.
- 세 시안이 같은 예시 데이터와 마크업을 쓰고 디자인 값(CSS)과 날짜 형식만 다르다(`shared.js`). 실제 사이트처럼 마크업 하나에 테마만 바꿔 비교하기 위해서다.
- 공용 스크립트를 불러오므로 파일을 바로 열지 말고 로컬 서버로 연다. 웹 폰트는 CDN에서 불러오므로 인터넷 연결이 필요하다.
  - `python3 -m http.server 4400 --directory docs/stages/3-ui-design` 뒤 `http://localhost:4400/` (Claude 데스크톱 앱에서는 `.claude/launch.json`의 `ui-mockups`)
- 화면 이동은 헤더 메뉴와 글 제목으로 한다. 주소는 `a-clean.html#/blog/` 형식이다.
  - 홈 `#/`, 포트폴리오 `#/portfolio/`, 소개 `#/about/`, 글 목록 `#/blog/`, 글 보기 `#/blog/building-this-site/`(여러 md 요소가 든 글)
- 모바일 모양은 브라우저 창을 좁히거나 개발자 도구의 기기 모드(375px)로 본다.

## 공통 사항

- 미니멀 원칙에 따라 세 시안 모두 한 단 구성, 장식 없는 배경, 강조색 하나로 만들었다. 방향은 글꼴, 배경 색감, 목록을 나누는 방식으로 갈랐다.
- 예시 데이터: 포트폴리오 4개(링크 없는 항목, 긴 설명 포함), 글 5개(긴 제목·설명, 수정일이 있는 글, 같은 날짜의 글 2개 포함). 글 보기의 이전·다음 글과 정렬 기준(같은 날짜면 slug 오름차순)도 design.md대로 동작한다.
- 디자인 값은 `@theme` 이름 형식의 CSS 변수(`--color-*`, `--font-*`, `--text-*`, `--leading-*`, `--spacing`, `--container-*`, `--radius-*`)로만 정의해 썼다. 간격은 Tailwind처럼 `--spacing`(0.25rem)의 배수다.
- 코드 블록은 틀(글꼴, 여백, 모서리)만 시안이고, 배경색과 문법 색은 6단계 하이라이팅 테마를 따른다.
- 한글 줄바꿈은 단어 단위(`word-break: keep-all`)로 하고, 긴 주소는 화면 안에서 줄바꿈한다.
- 확인 결과(2026-10-20): 세 시안 모두 홈, 포트폴리오, 소개, 글 목록, 글 보기(와 404)가 표시되고, 데스크톱(1024px 또는 1280px)과 모바일(375px) 폭에서 가로 스크롤이 없다.

## 시안 A: 깔끔한 기본형

- 콘셉트: 흰 배경에 고딕(Pretendard), 파란 강조색. 포트폴리오는 테두리 있는 카드 2열(모바일 1열). 가장 흔한 개발자 블로그 모양이다.
- 현재 메뉴: 글자를 진하게 하고 아래에 강조색 밑줄
- 이전·다음 글: 테두리 상자 두 개를 좌우로(모바일은 위아래로)
- 날짜: `2026년 10월 20일`
- 장점: 익숙해서 누구에게나 읽기 쉽고, 카드라 포트폴리오 항목이 잘 구분된다. 구현이 가장 단순하다.
- 단점: 개성이 적어 기억에 남기 어렵다.

## 시안 B: 글 중심 에디토리얼형

- 콘셉트: 미색 배경에 명조(Noto Serif KR) 본문, 적갈색 강조색. 헤더와 제목을 가운데 정렬하고, 상자 없이 구분선으로 항목을 나눈다. 글 목록은 넓은 화면에서 날짜를 왼쪽 칸에 둔다. 잡지나 책처럼 글을 읽는 데 맞춘 모양이다.
- 현재 메뉴: 강조색 글자와 밑줄
- 이전·다음 글: 굵은 구분선 아래 두 칸(모바일은 두 줄)
- 날짜: `2026. 10. 20.`
- 장점: 긴 글이 가장 편하게 읽히고, 차분하고 개성 있는 인상을 준다.
- 단점: 명조 웹 폰트가 무거워(한글 명조는 파일이 크다) 첫 표시가 늦을 수 있다. 개발 블로그로는 덜 흔한 인상이고, 코드와 명조 본문의 대비가 크다.

## 시안 C: 개발자 모노형

- 콘셉트: 고정폭 글꼴(JetBrains Mono)로 제목과 메뉴, 날짜를 쓰고 본문은 고딕. 초록 강조색과 마크다운 기호(`~/`, `#`, `##`, `>`)로 장식한다. 개발자 사이트라는 것이 바로 드러나는 모양이다. (고른 뒤 한글 문장은 고딕으로 바꿨다. 아래 "결정" 참고)
- 현재 메뉴: 강조색 `[블로그]`처럼 괄호로 감싼다
- 이전·다음 글: 점선으로 나눈 두 줄, `← 이전 글 제목` 형식
- 날짜: `2026-10-20`
- 장점: 개발자라는 정체성이 분명하고, 날짜·코드와 잘 어울린다. 목록이 촘촘해 한눈에 많이 보인다.
- 단점: 고정폭 글꼴에 한글이 없어 한글은 고딕으로 섞여 보이고, 고정폭 공백 때문에 한글 사이 간격이 넓어 보인다. 사업 파트너나 일반 방문자에게는 딱딱하게 느껴질 수 있다.

## 추천

- 시안 A를 바탕으로 하는 것을 추천한다. 방문자가 채용 담당자, 사업 파트너, 개발자, 일반 방문자로 넓어서 누구에게나 익숙하고 읽기 쉬운 쪽이 맞고, 미니멀 원칙과 구현 단순성에도 가장 잘 맞는다.
- 개성이 부족하다고 느끼면 하위 단계 2에서 다른 시안의 요소를 섞는 방법이 있다(예: B의 글 목록 날짜 왼쪽 칸, C의 날짜 형식 `2026-10-20`).

## 결정

- 2026-10-20: 사용자가 시안 C(개발자 모노형)를 골랐다(추천은 A였다).
- 2026-10-20: 시안 C의 단점이던 한글 간격 문제를 고쳤다. 고정폭 글꼴(JetBrains Mono)에는 한글이 없어 고딕으로 표시되는데, 공백은 고정폭 글꼴의 것을 써서 한글 문장의 띄어쓰기가 고딕보다 약 2.4배 넓었다(20px 기준 12px 대 5px).
  - 선택지: 한글 문장은 고딕으로 쓴다 / 한글이 있는 고정폭 글꼴(D2Coding 등)을 추가한다 / 그대로 둔다.
  - 결정: 한글이 들어가는 문장(제목, 소개, 링크명, 화면 문구)은 고딕으로 쓰고, 기호(`~/`, `#`, `>`, `[ ]`, `→`), 날짜, 사이트 이름만 고정폭으로 쓴다. 모노 느낌은 기호와 날짜로 유지하면서 웹 폰트를 늘리지 않기 위해서다(한글 고정폭 글꼴은 파일이 크다).
  - 함께 바꾼 것: 홈의 한 줄 소개가 고딕이 되면서 가늘어 보여 굵게 했다.
- 2026-10-20: 사용자가 다듬은 시안 C를 최종안으로 승인했다.
- 2026-10-20: 공통 UI로 옮기면서 두 가지를 정했다. 확정 값은 [design.md](../design.md#공통-ui)에 있다.
  - 흐린 글자색을 `#6e7781`에서 `#656d76`으로 조금 진하게 했다. 원래 색은 배경 대비가 4.43:1로, 날짜·설명 같은 작은 글자의 WCAG AA 기준(4.5:1)에 못 미쳤기 때문이다. 바꾼 색은 5.1:1이고 눈으로 보기에는 차이가 거의 없다. 시안 파일에도 반영했다.
  - 웹 폰트는 시안처럼 CDN에서 불러오지 않고 npm 패키지로 설치해 사이트와 함께 배포한다.
    - CDN: 설정이 가장 간단하지만, 방문할 때마다 외부 서버(jsDelivr, Google Fonts)에 요청해 방문자 정보가 넘어가고 그 서버 상태에 영향을 받는다.
    - npm 패키지로 함께 배포: 외부 요청이 없고 버전이 lockfile로 고정된다. 설치가 하나 늘어나는 정도의 부담이다.
- 2026-10-20: 검토(산출물만 보는 별도 검토)에서 나온 점을 반영했다.
  - 제목 굵기와 목록 기호를 design.md에 적었다. 시안은 브라우저 기본 스타일 덕분에 굵게 보였지만, Tailwind의 preflight가 이를 지우므로 문서에 없으면 4단계에서 다르게 구현되기 때문이다.
  - 날짜 줄의 "수정"을 고딕으로 바꿨다(한글은 고딕이라는 글꼴 규칙에 맞추기 위해서다).
  - 화살표 `→`, `←`는 JetBrains Mono 라틴 부분 집합에 없어 대체 글꼴로 표시된다는 것을 적었다. 모양은 시안과 같아 그대로 둔다.
  - 웹 폰트의 패키지 이름과 불러오는 방법은 4단계에서 정하기로 사용자가 받아들였다. 방식(npm으로 함께 배포, 부분 집합, 굵기)은 이 단계에서 정했다.

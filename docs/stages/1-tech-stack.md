# 1단계: 기술 스택 선정

목적과 끝난 상태는 [진행 계획](../plan.md)의 1단계를 따른다. 이 문서는 비교 과정과 결정 이유를 담고, 확정된 스택은 `docs/design.md`에 적는다.

- 상태: 완료(2026-10-20, 사용자 검토 통과)
- 버전은 2026-10-20 npm 기준이다. 실제 설치 버전의 원칙은 [design.md](../design.md#기술-스택)를 따른다.

## 비교 기준

[개요](../project_overview.md)의 원칙에서 가져온다.

- AI 주도 개발: Claude가 정확하게 다룰 수 있는지(문서·예제가 많고 널리 쓰이는지), 규칙이 단순해 일관되게 구현되는지
- 정적 빌드: 서버 없이 HTML로 빌드되는지
- GitHub Pages 배포: 하위 경로(`/<저장소명>/`)와 커스텀 도메인 둘 다 무리 없이 되는지
- md 블로그: md 파일에서 글 목록·글 보기를 만들고, 글 정보(frontmatter) 형식을 빌드 때 검증할 수 있는지
- SEO: 페이지마다 완성된 HTML이 나오는지, 메타 태그와 sitemap을 쉽게 넣을 수 있는지
- 그 밖에: 미니멀한 사이트에 비해 과하지 않은지(관리 부담)

## 1. 프레임워크

후보:

- Astro (7.x)
  - 장점: 콘텐츠 사이트용으로 만들어져 기본 출력이 순수 HTML이고 JS를 보내지 않는다. md 처리, 코드 하이라이팅(Shiki), 콘텐츠 컬렉션(글 정보와 데이터 파일을 스키마로 빌드 때 검증)이 내장돼 5·6단계 "형식이 틀리면 빌드 실패"를 별도 도구 없이 만족한다. `base` 설정으로 GitHub Pages 하위 경로를 처리하고 공식 배포 가이드와 Action이 있다. `.astro` 파일이 HTML에 가까워 구조가 단순하다.
  - 단점: Next.js보다 사용자·예제가 적다. 메이저 버전이 자주 올라 Claude가 예전 API로 쓸 수 있다(공식 문서 확인과 타입 검사로 막는다).
- Next.js (16.x, static export)
  - 장점: 가장 널리 쓰여 예제가 많다. React 생태계를 그대로 쓴다.
  - 단점: 서버 기능을 전제로 한 프레임워크라 static export에서는 쓸 수 없는 기능이 많다. md 블로그는 MDX·remark 설정, frontmatter 검증을 직접 조립해야 한다. 정적 페이지에도 React 런타임 JS가 실린다. 이 사이트에 비해 과하다.
- Eleventy (3.x)
  - 장점: 가장 단순한 정적 생성기이고 출력도 순수 HTML이다.
  - 단점: TypeScript·데이터 검증이 기본으로 없어 직접 붙여야 한다. 템플릿 언어 선택지가 많아 AI가 일관되게 쓰기 어렵다. 사용자·예제가 적다.

추천: Astro. 이 프로젝트의 요구(정적 HTML, md 블로그, 빌드 시 데이터 검증, GitHub Pages, SEO)가 Astro의 기본 기능과 거의 그대로 겹쳐서, 직접 조립할 부분이 가장 적다.

## 2. 스타일링과 UI 컴포넌트 라이브러리

후보:

- 순수 CSS(Astro 컴포넌트의 범위 지정 `<style>` + 전역 CSS 변수)
  - 장점: 의존성이 없다. 색·글꼴·간격을 CSS 변수로 두면 3단계 시안의 기본 값을 그대로 옮길 수 있다. 화면이 적은 미니멀 사이트에 충분하다.
  - 단점: 클래스 이름과 규칙을 직접 정해야 한다(2단계 코드 규칙에서 정한다).
- Tailwind CSS (4.x)
  - 장점: AI가 다루기 익숙하고, 디자인 값이 테마로 모인다.
  - 단점: 마크업이 길어져 읽기 어렵고, 화면이 적은 사이트에서는 이점이 작다.

UI 컴포넌트 라이브러리: 쓰지 않는다. 필요한 부품(헤더, 카드, 글 목록)이 적고, 라이브러리의 기본 디자인이 미니멀 원칙과 3단계 시안을 따르는 데 오히려 방해가 된다.

추천: 순수 CSS(범위 지정 스타일 + CSS 변수), UI 라이브러리 없음.

## 3. TypeScript, 패키지 매니저, lint·포맷터

- TypeScript: 사용한다(Astro의 strict 설정). 데이터 스키마와 컴포넌트 props의 실수를 빌드 전에 잡아, AI가 만든 코드의 오류를 자동으로 걸러준다.
- 패키지 매니저 후보:
  - pnpm: 빠르고 의존성을 엄격하게 관리한다. 단, 로컬과 CI에 따로 설치해야 한다.
  - npm: Node에 들어 있어 따로 설치할 것이 없다. 의존성이 적은 이 프로젝트에서는 속도 차이가 작다.
  - 추천: npm. 준비할 것이 하나 줄고 CI 설정도 단순하다.
- lint·포맷터 후보:
  - ESLint + Prettier: `.astro` 파일 지원 플러그인이 안정적이다. 단, 설정 파일과 의존성이 여럿이다.
  - Biome: 하나로 lint와 포맷을 하고 빠르다. 단, `.astro` 파일 지원이 아직 부분적이다.
  - 추천: ESLint(eslint-plugin-astro) + Prettier(prettier-plugin-astro). 코드 대부분이 `.astro` 파일이라 그 지원이 확실한 쪽을 고른다.

## 4. md 처리와 코드 하이라이팅

- md 처리: Astro 내장 md 처리와 콘텐츠 컬렉션을 쓴다. 글 정보(제목, 날짜 등)는 컬렉션 스키마로 정의해 빠지거나 틀리면 빌드가 실패하게 한다. MDX(md 안에 컴포넌트)는 지금 쓰지 않는다. 글은 순수 md로 충분하고, 필요해지면 공식 통합으로 추가할 수 있다.
- 코드 하이라이팅: Astro 내장 Shiki. 빌드 때 HTML로 색을 입혀 방문자 브라우저에서 JS가 필요 없다. 테마는 6단계에서 정한다.

## 5. 배포와 SEO 도구

- 배포: GitHub Actions에서 검증 → 빌드 → GitHub Pages 배포를 한다(공식 `actions/upload-pages-artifact`, `actions/deploy-pages` 사용). 검증이나 빌드가 실패하면 배포 작업이 실행되지 않게 한다. gh-pages 브랜치에 빌드 결과를 커밋하는 방식은 이력이 지저분해지고 권한 설정이 늘어서 쓰지 않는다.
- sitemap: 공식 `@astrojs/sitemap`.
- 메타 태그(noindex 포함): 공통 레이아웃에서 직접 넣는다(라이브러리 없이). 페이지 종류가 적어 직접 관리하는 편이 단순하다.
- robots.txt: 레이아웃이 아니라 별도 파일(정적 파일 또는 빌드 때 생성하는 엔드포인트)로 직접 만든다.
- 공개 전 수집 차단(robots.txt Disallow, noindex)은 4단계에서 만들고, 공개 전후를 어떻게 바꿀지(환경 변수 등)도 4단계에서 정한다. 메타 태그 전체의 구체적인 방식은 7단계에서 정한다.

## 6. 검증 도구

2단계 테스트 전략의 기본(빌드 시점 검증은 필수, 단위·화면 비교 테스트는 지금 하지 않음)에 맞춘다.

- 타입 검사: `astro check`(`.astro` 파일까지 포함한 TypeScript 검사)
- lint: ESLint, 포맷 검사: Prettier(`--check`)
- 데이터 형식 검증: Astro 콘텐츠 컬렉션 스키마(Zod). 별도 도구 없이 빌드가 실패한다.
- 빌드 결과 검사(메타 태그, sitemap 누락 확인): 7단계에서 빌드 결과 HTML을 읽는 간단한 스크립트로 한다.
- E2E 도구(Playwright 등): 쓰지 않는다. 화면이 적고 상호작용이 거의 없는 정적 사이트라 관리 부담에 비해 얻는 것이 적다. 필요해지면 추가한다.

## 추천안 요약

- 프레임워크: Astro
- 스타일링: 순수 CSS(범위 지정 스타일 + CSS 변수), UI 라이브러리 없음
- 언어: TypeScript(strict)
- 패키지 매니저: npm
- lint·포맷터: ESLint + Prettier(Astro 플러그인)
- md 처리: Astro 내장 md + 콘텐츠 컬렉션, MDX 없음
- 코드 하이라이팅: Astro 내장 Shiki
- 배포: GitHub Actions + 공식 Pages Action
- SEO: `@astrojs/sitemap`, 메타 태그·robots.txt는 레이아웃에서 직접
- 검증: `astro check`, ESLint, Prettier 검사, 콘텐츠 컬렉션 스키마, E2E 없음

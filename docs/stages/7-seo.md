# 7단계: SEO 기본

목적, 끝난 상태, 하위 단계는 [진행 계획](../plan.md)의 7단계를 따른다. 이 문서는 이 단계에서만 쓰는 구체적인 선택과 이유를 담고, 여러 단계가 따를 것은 [design.md](../design.md)에 적는다.

- 상태: 완료(2026-10-21). 하위 단계 1·2 모두 사용자 검토 통과

## 하위 단계 1: 메타 태그

### 작업 전 상태

- `BaseLayout`의 머리에는 `charset`, `viewport`, noindex(공개 전), `<title>`만 있다. 제목은 `<제목> - <활동명>`이고, 제목이 없는 홈은 `<활동명>`이다.
- 설명으로 쓸 수 있는 값: 글의 `description`(필수), 프로필의 `intro`(한 줄 소개), 포트폴리오 항목의 `description`. 포트폴리오 목록·블로그 목록 페이지 자체의 설명은 어디에도 없다.
- `public/`이 없어 파비콘과 OG 이미지가 없다. 브라우저는 `/favicon.ico`를 요청해 404를 받는다.

### 결정할 것과 추천

추천을 먼저 적고, 다른 선택지와 비교를 그 아래에 적는다.

- 결정(2026-10-21): 사용자가 1~8 모두 추천대로 정했다. 7·8의 모양은 시안 중에서 OG 이미지는 B(어두운 터미널), 파비콘은 A(투명 배경)를 골랐다(아래 [이미지](#이미지)). 결과 규칙은 [design.md](../design.md#메타-태그)에 있다.

1. 제목 형식
   - 추천: 지금 형식(`<제목> - <활동명>`, 홈은 `<활동명>`)을 유지한다. `og:title`은 뒤의 활동명을 뺀 페이지 제목만 쓰고(글은 글 제목), 활동명은 `og:site_name`으로 따로 알린다. 공유 미리보기에는 사이트 이름이 따로 표시되기 때문이다.
   - 다른 선택지: 홈을 `<활동명> - <한 줄 소개>`로 바꾸는 것. 검색 결과에서 무슨 사이트인지 바로 보이지만, 한 줄 소개는 설명에도 들어가므로 겹친다.

2. 페이지별 설명의 출처
   - 추천: 글은 `description`, 홈·소개는 프로필의 `intro`, 포트폴리오·블로그 목록은 페이지 코드에 쓴 고정 문구(예: "mivomad33이 만든 것과 참여한 프로젝트", "mivomad33의 개발·사업 기록". 활동명은 프로필 값으로 넣는다). 404는 설명을 넣지 않는다.
     - 화면 문구를 코드에 바로 쓰는 규칙([design.md](../design.md#코드-규칙))과 맞고, 목록 페이지마다 설명이 달라진다. 검색 엔진은 페이지마다 다른 설명을 권한다.
   - 다른 선택지:
     - 글이 아닌 페이지 모두 `intro`: 가장 단순하지만 홈·소개·목록 4개 페이지의 설명이 같아진다.
     - 프로필 데이터에 페이지별 설명 항목을 추가: 코드를 고치지 않고 바꿀 수 있지만, 자주 바꿀 값이 아닌데 데이터 형식과 스키마가 늘어난다.

3. canonical
   - 추천: 404를 뺀 모든 페이지에 `site` 기준 절대 주소(끝 `/` 포함)로 넣는다. 주소 끝 `/` 유무나 기본 주소(github.io)와 도메인 주소처럼 같은 페이지가 여러 주소로 보일 때 대표 주소를 알려 준다. 8단계에서 `site`만 바꾸면 따라 바뀐다.

4. OG·Twitter 카드 태그
   - 추천: `og:type`(글은 `article`, 나머지는 `website`), `og:title`, `og:description`, `og:url`(canonical과 같은 값), `og:site_name`, `og:locale`(`ko_KR`), OG 이미지를 두면 `og:image`와 대체 텍스트·크기. Twitter(X)는 OG 태그를 대신 읽으므로 `twitter:card`만 넣는다(이미지가 있으면 `summary_large_image`, 없으면 `summary`).

5. 페이지 종류별 태그
   - 추천: 홈·포트폴리오·블로그 목록·소개·글 보기는 위의 태그를 모두 넣는다. 글 보기는 6의 날짜 정보를 더 넣는다. 404는 제목·파비콘만 넣고 설명·canonical·OG 태그를 넣지 않는다. 404는 없는 모든 주소에 같은 내용으로 나가므로 대표 주소가 없고, 공유될 일도 없다.

6. 글의 작성·수정일을 알리는 곳
   - 추천: 구조화 데이터(JSON-LD `BlogPosting`의 `datePublished`, `dateModified`)와 OG `article:published_time`, `article:modified_time`. 수정일은 `updated`가 있을 때만 넣는다. sitemap `lastmod`는 쓰지 않는다.
     - 구조화 데이터는 Google이 글의 날짜를 읽는 곳으로 안내하는 방법이다. OG 날짜 태그는 같은 값을 한 줄씩 더 쓰는 것이라 비용이 거의 없다.
     - `lastmod`는 글이 아닌 페이지(홈, 목록)의 수정 시점을 정확히 줄 방법이 없고, Google은 `lastmod`가 정확하지 않으면 무시한다. 글에만 넣으려면 sitemap 설정에서 주소마다 글을 찾아 붙여야 해 하위 단계 2가 복잡해진다.
     - 구조화 데이터는 `<script type="application/ld+json">`으로 넣는다. 실행되는 스크립트가 아니라 데이터이므로 클라이언트 JS를 쓰지 않는다는 규칙과 부딪히지 않는다.
   - 다른 선택지: 날짜 태그만(구조화 데이터 없이), 또는 셋 다.

7. OG 이미지
   - 추천: 모든 페이지가 같이 쓰는 고정 이미지 하나(1200×630 PNG). 활동명과 한 줄 소개를 공통 UI의 색·글꼴로 넣은 모양으로 Claude가 만들고, 사용자가 시안 중에서 고른다. 메신저나 SNS에 링크를 붙였을 때 큰 미리보기가 나온다.
   - 다른 선택지:
     - 두지 않는다: 가장 단순하지만 공유 미리보기에 이미지가 없거나 작은 카드로 나온다.
     - 글마다 제목을 넣은 이미지를 빌드 때 만든다(satori 등): 공유가 가장 보기 좋지만, 의존성과 빌드 시간이 늘어 "기본"의 범위를 넘는다. 공개 뒤 필요하면 따로 변경으로 한다.

8. 파비콘
   - 추천: 넣는다. 헤더의 `~/` 기호를 강조색으로 쓴 모양을 Claude가 SVG로 만들고, SVG를 지원하지 않는 곳을 위해 PNG(`apple-touch-icon` 180×180 등)도 함께 둔다. 검색 결과의 사이트 이름 옆과 브라우저 탭에 보인다.
   - 다른 선택지: 사용자가 준비한 로고를 쓴다. 지금 로고가 없으므로, 나중에 생기면 파일만 바꾼다.

### 이미지

- 시안: OG 이미지는 A(사이트 헤더·푸터 모양, 밝은 배경과 점선), B(어두운 터미널 화면, `$ whoami` 아래 활동명과 커서), C(밝은 배경에 큰 `~/활동명`과 왼쪽 강조색 띠) 3개, 파비콘은 A(투명 배경에 강조색 `~/`), B(어두운 둥근 칸에 밝은 초록 `~/`) 2개를 만들었다. 고르지 않은 시안 파일은 지웠다(git 이력에 있다).
- 고른 것: OG 이미지 B, 파비콘 A.
  - OG 이미지 B는 사이트(밝은 배경)와 분위기가 다르지만, 공유 미리보기에서 눈에 띄고 개발자 사이트라는 것이 바로 드러난다. 강조색은 어두운 배경에서 대비가 낮아 사이트의 `#1a7f37` 대신 밝은 초록(`#4ac26b`)을 썼다.
  - 파비콘 A는 헤더의 `~/`와 같은 모양이다. 글꼴 없이 선으로 그려 어떤 환경에서도 같게 보인다.
- 원본과 만드는 방법: 원본은 `docs/stages/7-seo/`의 `og-image.html`(글꼴은 `_fonts.css`가 `node_modules`의 사이트 글꼴 파일을 읽는다)과 `favicon.svg`다. `make-images.sh`가 macOS의 Google Chrome(헤드리스)으로 `public/`에 `og.png`, `favicon.svg`, `favicon-96.png`, `apple-touch-icon.png`를 만든다.
  - 이미지 처리 패키지(sharp)는 Astro가 설치하지만 직접 의존성이 아니라 불러올 수 없어(pnpm), 패키지를 추가하지 않고 Chrome으로 렌더링했다. 만든 PNG를 저장소에 올리므로 빌드와 CI는 Chrome이 필요 없다.
  - `favicon-96.png`는 SVG 파비콘을 지원하지 않는 브라우저용이다(Google 검색 결과는 48의 배수 크기를 권한다). `apple-touch-icon.png`(180×180)는 iOS 홈 화면용이며, 투명 부분이 검게 보이므로 사이트 배경색 위에 여백을 두고 넣었다.
  - `/favicon.ico`는 두지 않는다. 링크 태그가 있으면 브라우저는 그것을 쓰고, `.ico`를 만들려면 도구가 더 필요하기 때문이다.

### 검토에서 고친 것(2026-10-21)

- 홈 `h1`: 5단계에서 "필요하면 7단계에서 다룬다"고 미뤄 둔 항목이다. 홈에만 `h1`이 없어 검색 엔진과 화면 낭독기가 페이지의 주제를 알기 어려우므로, 활동명을 화면에 보이지 않는 `h1`(`sr-only`)로 넣었다. 시안 구조(헤더의 사이트 이름이 제목 역할)를 바꾸지 않기 위해서다.
- OG 이미지의 글자와 프로필: 공개 뒤에는 프로필 변경을 main에 바로 push할 수 있어(콘텐츠 예외), 이미지를 다시 만들지 않으면 옛 값이 남고 CI도 잡지 못한다. 규칙에 기대지 않고, 하위 단계 2의 빌드 결과 검사가 원본의 글자와 프로필 값을 비교하게 했다([plan.md](../plan.md) 하위 단계 2). 콘텐츠 예외는 그대로 둔다(검사가 실패하면 배포되지 않으므로).
- `make-images.sh`: 출력 위치를 실행한 폴더가 아니라 스크립트 위치 기준으로 바꿨다(다른 폴더에서 실행해도 저장소의 `public/`에 만든다). Chrome은 글꼴 파일이 없어도 대체 글꼴로 조용히 그리므로, `_fonts.css`가 읽는 글꼴 파일이 없으면 멈추게 했다. 다른 폴더에서 실행해 결과가 같은 것과, 글꼴이 없는 복사본에서 실패하는 것을 확인했다.
- 이 절의 "작업 전 상태" 제목: 구현 뒤에는 맞지 않는 내용이라 제목을 바꿨다.

### 구현

- `BaseLayout`의 props: 일반 페이지는 `title`(홈은 없음), `description`(필수), 글 보기는 `article`(게시일·수정일)을 더 넘긴다. 404는 `notFound`를 넘기며, 이때는 `description`을 받지 않는다(타입으로 막는다).
- 구조화 데이터는 `src/lib/seo.ts`의 `blogPostingJsonLd`가 만든다. 글 제목에 `</script>`가 있어도 태그가 끝나지 않게 `<`를 이스케이프한다. 저자는 활동명과 소개 페이지 주소, 이미지는 OG 이미지다.
- 포트폴리오 목록의 설명은 "`<활동명>`의 포트폴리오. 만든 것과 참여한 프로젝트."다. "`<활동명>`이 만든"처럼 쓰면 활동명에 따라 조사가 달라지므로 "의"를 썼다.

### 확인 결과(2026-10-21)

- `pnpm verify`가 통과했다(10페이지).
- 빌드 결과의 10개 HTML을 모두 읽어 확인했다.
  - 404를 뺀 9개 페이지에 정한 태그가 모두 있고, 값이 페이지에 맞다(글은 글의 제목·설명, 목록·홈·소개는 정한 설명). canonical·`og:url`·`og:image`는 `https://mivomad33.github.io/` 기준 절대 주소이고 끝에 `/`가 있다.

  - 404에는 제목·파비콘·noindex만 있고 설명·canonical·OG 태그·JSON-LD가 없다.
  - 10개 페이지 모두 noindex가 그대로 있다.

## 하위 단계 2: sitemap·robots.txt와 빌드 결과 검사

### sitemap과 robots.txt

- `@astrojs/sitemap` 3.7.4를 설치해 `astro.config.mjs`의 통합으로 넣었다. 빌드하면 `sitemap-index.xml`과 `sitemap-0.xml`이 생기고, 404는 설정 없이 빠진다(빌드 결과로 확인).
  - `lastmod`는 넣지 않는다(하위 단계 1의 결정 6).
- robots.txt에 `Sitemap: <사이트 주소>/sitemap-index.xml`을 넣었다. 수집을 막는 동안에도 넣는다. `Disallow: /`가 있으면 크롤러가 어차피 읽지 않고, 공개 때 `ALLOW_INDEXING`만 바꾸면 되게 하기 위해서다.
- 사이트 주소: `astro.config.mjs`에 있던 `site` 값을 `src/lib/site.ts`의 `SITE`로 옮기고, 설정이 그 값을 읽게 했다. 빌드 결과 검사(Node로 실행)도 같은 값을 써야 하는데, 설정 파일을 불러오면 Tailwind 등 빌드 도구까지 함께 불러오게 되기 때문이다. 8단계에서 바꿀 곳도 `site.ts` 한 파일(`SITE`, `ALLOW_INDEXING`)로 모인다.
- 절대 주소 만들기(`siteUrl()`)도 `site.ts`로 옮겼다. 레이아웃(canonical, OG), robots.txt, 검사가 같이 쓴다. 레이아웃은 `Astro.site` 대신 이 함수를 쓴다.

### 빌드 결과 검사

- 스크립트: `scripts/check-build.ts`. 검사 항목은 [design.md 테스트 전략](../design.md#테스트-전략)에 있다. 문제를 모두 모아 한 번에 보여 주고 실패로 끝난다. 구조화 데이터를 JSON으로 읽지 못하거나 `dist/`가 없을 때도 예외로 멈추지 않고 오류 목록에 넣는다.
- 실행: `pnpm build`를 `astro build && node scripts/check-build.ts`로 바꿨다.
  - CI의 빌드 작업이 `pnpm build`를 부르므로 워크플로를 고치지 않아도 검사가 들어가고, 실패하면 배포 작업이 실행되지 않는다. 로컬의 `pnpm verify`도 같다.
  - 별도 명령으로 두면 CI와 로컬 양쪽에 따로 넣어야 하고, 빼먹으면 검사 없이 배포된다.
  - Node 24가 타입 표기를 지우고 TS 파일을 바로 실행하므로(타입 검사는 하지 않는다) 실행 도구를 추가하지 않았다. 타입 검사와 lint는 `pnpm check`가 이 파일도 함께 한다. 그래서 `site.ts`를 확장자까지 적어 불러온다.
- HTML 읽기: Astro가 만든 HTML만 읽고 속성 값이 항상 큰따옴표라 정규식으로 태그를 읽는다. HTML 파서 패키지를 추가하지 않기 위해서다. Astro는 속성 값 안의 `<`, `>`를 이스케이프하지 않으므로(`&`, `"`만 바꾼다), 태그 끝을 찾을 때 따옴표 안은 건너뛴다.
- 글 보기 구분: `og:type`이 아니라 글 파일 목록(`src/content/blog/*.md`의 slug)으로 한다. `og:type`이 빠지거나 틀린 것도 잡고, 나중에 `/blog/` 아래에 글이 아닌 페이지를 만들어도 글로 잘못 보지 않기 위해서다. 글마다 글 보기 페이지가 있는지도 본다.
- OG 이미지 원본 비교: `og-image.html`의 활동명과 한 줄 소개에 `data-profile` 표시를 달고, 그 글자(`&amp;` 같은 엔티티는 풀어서)를 `profile.yaml`의 값과 비교한다. 다르면 이미지를 다시 만드는 명령을 오류에 함께 보여 준다. 원본만 고치고 이미지를 다시 만들지 않은 것은 잡지 못한다(PNG의 글자까지 비교하려면 이미지 처리 도구가 필요해 범위를 넘는다).
- 검사가 dist/ 밖의 파일(`docs/stages/7-seo/og-image.html`, `src/data/profile.yaml`)도 읽는다. 이미지의 원본이 docs/에 있어서다. 원본을 옮기면 검사의 경로도 고친다.

### 검토에서 고친 것(2026-10-21)

- 제목·설명·한 줄 소개에 `<`, `>`가 있으면 정상 글인데도 검사가 실패했다(Astro가 속성 값 안의 `<`, `>`를 그대로 두는데, 검사가 그 `>`에서 태그가 끝난 것으로 읽었다). 태그 끝을 찾을 때 따옴표 안을 건너뛰게 고쳤다.
- 글 보기를 주소 형식 대신 글 파일 목록으로 구분하게 고쳤다(`/blog/` 아래 글이 아닌 페이지를 글로 잘못 보던 것). 글마다 글 보기 페이지가 있는지도 확인한다.
- 구조화 데이터를 JSON으로 읽지 못하거나 `dist/`가 없을 때 예외로 멈추던 것을 오류 목록에 넣게 고쳤다.
- 놓치던 경우를 잡게 했다: 파비콘 주소가 비었을 때, 같은 메타 태그·canonical이 두 번 있을 때, robots.txt에 허용과 차단이 함께 있을 때, `og:locale`(`ko_KR`)·`twitter:card`(`summary_large_image`)·`og:site_name`(활동명)·`og:description`(`description`과 같음)의 값이 틀렸을 때.

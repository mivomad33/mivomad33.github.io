# 6단계: 블로그

목적, 끝난 상태, 하위 단계는 [진행 계획](../plan.md)의 6단계를 따른다. 이 문서는 이 단계에서만 쓰는 구체적인 선택과 이유를 담고, 여러 단계가 따를 것은 [design.md](../design.md)에 적는다.

- 상태: 완료(2026-10-21). 하위 단계 1·2·3 모두 사용자 검토 통과

## 하위 단계 1: 글 데이터와 글 목록·홈 최근 글

### 로더

먼저 Astro 7.4의 기본 `glob()` 로더 소스와 실제 빌드로 동작을 확인했다.

- 오류 처리: 4단계의 `file()` 로더와 달리, 파일 읽기 결과가 없을 때를 빼면 frontmatter 문법 오류·스키마 오류를 그대로 던져 빌드가 멈춘다. 이전 빌드 데이터(`node_modules/.astro/data-store.json`)가 있어도 숨기지 않는다. 내용이 바뀌지 않은 파일만 이전 결과를 다시 쓰는데, 그 결과는 이미 검증을 통과한 것이라 문제가 없다.
- 문제 1, 파일 이름: 기본 `id`는 파일 이름을 slug 형식으로 바꾼 값이라 `Hello_World.md`도 `hello_world`처럼 통과하고, frontmatter에 `slug`가 있으면 그 값을 쓴다. 패턴 밖의 하위 폴더 글과, 처리 방법이 없는 확장자(`.MD`, `.markdown`)는 경고만 남기거나 아무 말 없이 건너뛴다(`generateId`도 부르지 않는다).
- 문제 2, 날짜: Astro는 frontmatter를 읽을 때 `2026-10-20` 같은 값을 Date로 바꾼다. 이때 `2026-13-45`는 오류 없이 2027-02-14가 되고, `2026-2-3`도 통과한다. 바뀐 Date에서는 원래 적은 값을 알 수 없어, 스키마만으로는 막을 수 없다.

그래서 `glob()`을 감싼 `blogLoader`(`src/lib/blog-loader.ts`)를 만들었다.

- 파일 검사: 기본 로더를 부르기 전에 글 폴더를 직접 훑어, `images/` 아래와 `.`으로 시작하는 파일(`.DS_Store` 등)을 뺀 모든 파일이 폴더 바로 아래의 `<slug>.md`가 아니면 빌드를 멈춘다. slug는 영문 소문자·숫자를 하이픈 하나로 이은 이름이다(하이픈 연속, 맨 앞·뒤 하이픈 불가). 기본 로더는 위처럼 건너뛰는 파일에 `generateId`를 부르지 않으므로, 이름 검사를 `generateId`에 두면 이런 파일을 잡지 못한다.
- `generateId`: 확장자를 뺀 파일 이름을 그대로 id(slug)로 쓴다.
- `parseData`를 감싸, 스키마에 넘기기 전에 파일의 frontmatter를 YAML 기본 규칙(날짜 변환 없음)으로 다시 읽어 넘긴다. 날짜가 적힌 문자열 그대로 스키마에 가므로, 스키마가 `z.iso.date()`로 형식과 실제 날짜(2월 30일 등)를 검사한 뒤 UTC 자정의 Date로 바꾼다.
  - 다른 방법으로 `entryTypes`의 md 처리 함수를 바꾸는 방법도 있었지만, `entryTypes`는 로더 문맥의 공개 타입에 없는 내부 값이라 Astro를 올릴 때 깨질 수 있어 쓰지 않았다. `parseData`와 `filePath`는 공개 API다.
  - frontmatter를 찾는 정규식은 Astro(`@astrojs/internal-helpers`의 `frontmatterRE`)와 같게 둔다. 다르면 Astro는 읽은 글(맨 앞 빈 줄, `---` 뒤 공백 등)을 여기서 못 읽어 실제 원인과 다른 오류가 난다. 문법 오류는 보통 Astro가 먼저 잡지만(파일 위치 표시), 여기서 나는 오류에도 파일 경로를 붙인다. `+++`(TOML)는 쓰지 않는다는 오류로 멈춘다. frontmatter가 없으면 빈 객체를 넘겨 필수 항목 누락으로 실패한다.
- 스키마(`src/content.config.ts`): `strictObject`라 `slug`나 오타 키는 실패한다. `updated`가 `date`보다 이르면 실패한다(같은 날은 통과).
- 글이 0개면(폴더가 없을 때 포함) 빌드는 통과하고 `The base directory ... does not exist` 경고가 나온다. git은 빈 폴더를 올리지 않으므로 글을 모두 지우면 폴더도 사라지는데, 이때도 정상 동작이다.

### 이미지

- 방식: `src/content/blog/images/<slug>/`에 두고 본문에서 `./images/<slug>/파일` 상대 경로로 넣는다([design.md](../design.md#데이터-파일-형식)).
- 비교한 방법:
  - 글마다 폴더(`<slug>/index.md`와 이미지): 이미지가 글 옆에 있지만, 글 파일 구조와 slug 규칙(파일 이름 = slug)이 바뀐다.
  - `src/assets/blog/`: 처리 결과는 같지만 본문 경로가 `../../assets/blog/...`로 길어진다.
  - `public/images/`: 빌드 처리 없이 그대로 복사된다. 크기를 줄이지 않고, 파일이 없어도 빌드가 통과한다(확인함).
  - 고른 방식은 글 파일 구조(`<slug>.md`)를 그대로 두면서, 경로가 짧고, Astro 이미지 처리를 받는다. 글 로더는 `.md`만 읽으므로 이미지 폴더는 글로 읽히지 않는다.
  - 검토에서 글마다 폴더 방식과 다시 비교했다(2026-10-20). 이미지가 없는 글이 대부분이면 글이 파일 하나로 남는 지금 방식이 낫고, 글마다 폴더 방식은 모든 글 파일이 `index.md`가 되며 slug 규칙·로더를 다시 바꿔야 한다. 사용자가 지금 방식을 유지하기로 했다. 글마다 이미지를 많이 넣게 되면 첫 글 공개 전에 다시 볼 수 있다(공개 뒤에는 주소를 바꾸지 않으므로).
- 확인(임시 글 보기 페이지로): 1200×600 PNG를 넣으면 `width`·`height`가 붙은 webp로 바뀌었고(`loading="lazy"`), 없는 파일을 넣으면 `ImageNotFound`로 빌드가 실패했다. 실제 글 보기에서의 표시는 하위 단계 2에서 확인한다.
- 대체 텍스트는 자동으로 검사하지 않는다(빈 `![](...)`도 빌드가 통과한다). 규칙으로만 둔다.

### 데이터와 화면

- 가져오기: `src/lib/blog.ts`의 `getPosts()`(게시일 최신순, 같으면 slug 오름차순)와 `getRecentPosts()`(최신 3개).
- 날짜: `src/lib/format-date.ts`의 `formatDate()`(UTC 기준 `YYYY-MM-DD`)와 `PostDate` 컴포넌트(`<time>`, 고정폭·`text-sm`·흐린 글자색). 글 보기(하위 단계 2)도 같이 쓴다.
- 컴포넌트: `PostListItem`(날짜·제목·설명, 제목 단계를 받는다. 글 목록은 `h2`, 홈은 `h3`)과 `PostList`(목록과 항목 사이 간격). 글이 0개일 때의 안내 문구는 포트폴리오 페이지와 같이 `EmptyNotice`를 쓴다. 넓은 화면의 2칸 격자는 소개 페이지와 같은 `grid-cols-label` 유틸리티를 쓴다.
- 샘플 글: 시안의 예시 5개를 md로 옮겼다(긴 제목·설명과 `updated`가 있는 글, 같은 날짜의 글 2개, 제목 단계·목록·인용·코드 블록·링크·긴 주소가 든 본문). 제목에 `:`가 있는 글은 YAML 규칙 때문에 따옴표로 감쌌다. 8단계 전에 실제 글로 바꾸거나 지운다(8단계에서 이미지와 함께 모두 지웠다).

### 확인 결과(2026-10-20)

- `pnpm verify` 통과.
- 이전 빌드 데이터가 있는 상태에서 아래를 하나씩 넣으면 모두 빌드가 실패했다(복원 뒤 다시 성공).
  - 필수 항목(`description`) 누락, 정해지지 않은 키(`tags`), `slug` 키
  - 형식이 틀린 날짜: `2026-13-45`, `2026-2-3`, `2026-02-30`, `2026/09/28`, 시각 포함(`2026-09-28T10:00:00+09:00`)
  - `date`보다 이른 `updated`, frontmatter 문법 오류, frontmatter 없음
  - 형식이 틀린 파일 이름(`Hello_World.md`), 하위 폴더의 글(`sub/nested.md`)
- 따옴표로 감싼 날짜(`"2026-09-28"`)와 `date`와 같은 날의 `updated`는 통과했다.
- 빌드 미리보기의 `/blog/`와 홈의 최근 글을 시안과 데스크톱(1024px)·모바일(375px)에서 비교했다. 목록 간격(24px), 항목의 칸 구성(날짜 78px·간격 20px), 날짜·제목·설명의 위치·크기·글꼴·색이 시안과 같았고, 가로 스크롤이 없다. 순서는 최신순이고 같은 날짜(09-28)는 `hello-world`, `retrospective-8-years` 순이다. 홈은 최신 3개만 보인다.
- 글이 0개(폴더 없음)면 빌드가 통과하고 `/blog/`에 "아직 항목이 없습니다."가 보이며 홈의 최근 글 영역이 사라졌다.
- 글 보기 페이지는 하위 단계 2에서 만들므로 목록의 링크는 아직 404다.

### 검토에서 고친 것(2026-10-20)

별도 서브에이전트 검토에서 나온 다섯 가지를 모두 고쳤다.

- frontmatter 정규식이 Astro보다 엄격해, 맨 앞 빈 줄이나 `--- `(뒤 공백)가 있는 정상 글이 `title: Required`로 실패하고, 일부 경우 오류 위치가 라이브러리 파일로 나왔다. 정규식을 Astro와 같게 하고 오류에 파일 경로를 붙였다.
- `.MD`, `.markdown` 파일이 오류 없이 빠졌다. 글 폴더를 직접 훑는 파일 검사로 바꿨다(위 로더).
- slug 규칙(하이픈 연속, 맨 앞·뒤 하이픈 불가)이 design.md와 오류 메시지에 없었다. 둘 다에 적었다.
- design.md 디렉터리 구조에 이미지 폴더(`src/content/blog/images/<slug>/`)를 추가했다.
- 빈 목록 안내 문구가 포트폴리오·글 목록 페이지에 따로 있었다. `EmptyNotice` 컴포넌트로 뽑았다.
- 다시 확인: `pnpm verify` 통과. 맨 앞 빈 줄, 여는·닫는 `---` 뒤 공백(본문 수평선 포함), BOM, CRLF, 따옴표 날짜는 통과하고, 위 실패 목록 전부와 TOML frontmatter, `a--b.md`, `-a.md`, `Post.MD`, `x.markdown`은 실패했다. `images/` 안의 파일과 `.DS_Store`는 통과했다.

## 하위 단계 2: 글 보기 페이지

- 상태: 완료(2026-10-21, 사용자 검토 통과). 하이라이팅 테마 `github-light-default`, 코드 합자 끄기(2026-10-20), 표 A안과 점선 수평선(2026-10-21)을 사용자가 골랐다.

### 페이지와 데이터

- `src/pages/blog/[slug].astro`: 글마다 페이지를 만든다. 제목(`h1`, `text-2xl` 굵게), 게시일과 수정일(`PostDate`, 수정일 앞에 `·` 와 "수정"), 본문, 이전·다음 글.
- 이전·다음 글: `src/lib/blog.ts`의 `getPostsWithNeighbors()`가 글 목록과 같은 순서(`getPosts()`)에서 바로 더 오래된 글을 이전 글, 바로 더 최신 글을 다음 글로 붙인다. 없는 쪽은 링크를 만들지 않고, 둘 다 없으면 영역도 만들지 않는다.
- 본문 모양: `Prose` 컴포넌트(`src/components/Prose.astro`)의 `<style>`로 정한다. md에서 만든 본문에는 클래스를 달 수 없기 때문이다(design.md 코드 규칙). 색·글꼴·글자 크기·간격은 테마 변수(`var(--spacing)`, `var(--color-accent)` 등)로 쓰고, 선 두께(`1px`, `2px`)와 밑줄 위치(`0.2em`)만 시안·design.md의 값을 그대로 쓴다.
  - Tailwind는 쓰인 테마 변수만 CSS에 넣는데, 컴포넌트 `<style>`의 `var(--text-lg)` 같은 참조도 쓰인 것으로 보고 넣는다(`text-lg`는 다른 곳에서 쓰지 않는데 빌드 결과에 있다).
  - 시안에서 브라우저 기본값에 기대던 것(제목 굵기, 순서 있는 목록의 숫자)은 Tailwind preflight가 지우므로 직접 정했다.

### 이미지

- 샘플 글(`building-this-site`)에 `images/building-this-site/page-layout.png`(800×400, 페이지 구성도)를 넣었다. 빌드 결과는 `width="800" height="400"`과 대체 텍스트가 붙은 webp이고, 화면 폭에 맞게 줄어든다(375px 폭에서 335×168).
- 여러 크기를 만드는 설정(`srcset`)은 하지 않았다. 본문 폭이 최대 46rem(736px)이라 원본 크기 하나로 충분하고, 설정을 늘리지 않기 위해서다. 큰 사진을 많이 넣게 되면 다시 본다.

### 하이라이팅 테마

- 기준: 밝은 배경의 사이트와 어울리고, 글자색과 배경의 대비가 WCAG AA(4.5:1) 이상일 것(design.md의 다른 색과 같은 기준).
- Shiki 4.5의 밝은 테마 20개에서 주요 토큰(주석, 문자열, 키워드, 숫자, 함수·타입 이름, 변수, 구두점)의 대비를 계산했다. AA를 넘는 것은 세 개뿐이다.
  - `github-light-default`: 가장 낮은 대비 4.55(주석). 사이트 색(글자 `#1f2328`, 흐린 글자, 구분선, 초록 강조)이 GitHub 색 체계라 같은 계열이다.
  - `github-light-high-contrast`: 가장 낮은 대비 5.04(주석). 같은 계열에서 더 진하다.
  - `light-plus`(VS Code 기본 밝은 테마): 가장 낮은 대비 4.59(타입 이름).
  - 나머지(예: `one-light` 2.47, `vitesse-light` 2.34, `min-light` 1.76)는 주석이 흐려 AA에 못 미친다.
- 세 테마 모두 코드 블록 배경은 흰색(`#ffffff`)이고, 페이지 배경(`#fcfcfc`)과는 구분선 색 테두리로 나뉜다.
- 세 테마를 같은 코드 예시(TypeScript, YAML, 셸)로 나란히 보여 주는 비교 화면을 만들어 사용자가 골랐다. 결정: `github-light-default`. 사이트 색과 같은 계열이고 AA를 넘는다.

### 코드 합자

- 코드 글꼴 JetBrains Mono는 합자가 기본으로 켜져 있어 `=>`가 `⇒`, `!==`가 `≢`처럼 보인다. 테마 비교 중에 발견했다.
- 결정: 끈다(`Prose`의 `code`에 `font-variant-ligatures: none`, 인라인 코드와 코드 블록 모두). 블로그 독자가 코드를 읽고 따라 칠 때 실제 글자와 다르게 보이면 헷갈리기 때문이다. 사용자가 골랐다.

### 표와 수평선

- 시안과 design.md에 없던 요소다. 검토에서 Tailwind preflight가 표의 테두리·간격을 지워 md 표가 읽기 어렵다는 점이 나와 이 하위 단계에서 정했다(2026-10-21).
- 표 후보 세 개(A 가로선만, B 격자, C 제목 줄 면 + 가로선)를 같은 표로 보여 주는 비교 화면을 만들어 사용자가 골랐다. 결정: A안. 제목 줄 아래 본문 글자색 실선, 행 사이 구분선 색 점선이다. 상자 없이 가는 사이트에서 표만 무거워지지 않고, 헤더·푸터의 점선과 같은 결이기 때문이다.
- 수평선: 헤더·푸터와 같은 구분선 색 점선, 위아래 간격 `--spacing`의 10배. 사용자가 골랐다.
- 표는 `display: block`과 `overflow-x: auto`로 넘치면 표 안에서 가로 스크롤된다. 처음에는 사이트 전체의 `overflow-wrap: anywhere` 때문에 칸이 넘치지 않고 "단/계"처럼 글자 단위로 쪼개졌다. 칸에서는 `overflow-wrap: normal`로 단어 단위 줄바꿈만 하게 고쳤다.
- 확인: 샘플 글에 표(4칸, 인라인 코드 포함)와 수평선을 넣었다. 375px에서 단어가 쪼개지지 않고 표가 화면 안에 들어갔다. 6칸에 긴 주소가 든 임시 글로는 표 안에서만 가로 스크롤되고(표 675px, 보이는 폭 335px) 페이지에는 가로 스크롤이 없었다(확인 뒤 지웠다).

### 확인 결과(2026-10-20)

- `pnpm verify` 통과.
- 빌드 미리보기의 글 보기를 시안과 데스크톱(1024px)에서 비교했다. 제목·날짜 줄, 본문 요소(문단, `h2`·`h3`과 기호, 목록, 인용, 링크, 인라인 코드, 코드 블록의 여백·테두리·줄 높이), 이전·다음 글 영역의 위치·크기·글꼴·색이 시안과 같았다.
- 모바일(375px)에서 가로 스크롤이 없고, 긴 코드 줄은 코드 블록 안에서만 가로 스크롤된다. 이전·다음 글은 표시와 제목이 두 줄로 쌓인다.
- 이전·다음 글이 목록 순서와 맞고, 가장 최신 글에는 이전 글만, 가장 오래된 글에는 다음 글만 있다.
- md 파일을 하나 추가하면 글 보기가 생기고 목록·홈의 최근 글·기존 글의 이전·다음 글에 반영됐다(확인 뒤 지웠다).

## 하위 단계 3: 공개 뒤 콘텐츠 반영 방식

- 상태: 완료(2026-10-21, 사용자 검토 통과). 사용자가 A안을 골랐다.

### 문제

- 개요의 목표는 "md 파일을 추가하고 push하면 자동 배포"인데, CLAUDE.md는 "main에 직접 커밋하지 않는다(이력을 깔끔하게 유지하기 위해)"이다. 공개 뒤에 글을 쓸 때 두 문구가 충돌한다.
- 어느 방식이든 워크플로(검증 → 빌드 → 배포, `needs`로 이어짐)가 같은 안전장치를 준다. 오류가 있는 글이 main에 올라가도 검증·빌드에서 멈추고, 사이트는 직전 정상 버전 그대로다. 그래서 방식의 차이는 안전보다 절차의 무게와 규칙의 단순함에 있다.

### 선택지

- A. 콘텐츠만 main에 바로 push: 개요 목표를 그대로 지키고 절차가 가장 가볍다(GitHub 웹·모바일에서도 고칠 수 있다). 규칙에 예외가 하나 생기고, 로컬 확인 없이 push한 글이 틀리면 main이 잠시 빌드 실패 상태가 되며 고침 커밋이 하나 더 생긴다.
- B. 콘텐츠도 작업용 브랜치 → main 머지: 규칙이 하나라 단순하고 main에는 검증된 것만 들어간다. 글마다 브랜치·머지·삭제가 필요하고, 개요 목표 문구를 "머지하면 배포"로 바꿔야 한다.
- C. 작업용 브랜치 + PR 자동 머지: main 보호와 가벼운 절차를 둘 다 얻지만, 저장소 설정(브랜치 보호, 자동 머지)을 사용자가 바꿔야 하고 움직이는 부분이 늘어 혼자 쓰는 블로그에는 과하다.

### 결정

- A안. 브랜치를 거쳐 얻는 안전이 크지 않고(틀린 글은 어느 쪽이든 배포되지 않는다), 개요의 목표 문구를 그대로 지키며, 글 하나가 커밋 하나라 "이력을 깔끔하게"라는 원래 이유도 거의 해치지 않기 때문이다.
- 적용 범위:
  - 콘텐츠: 블로그 글과 이미지(`src/content/blog/`), 프로필·포트폴리오 데이터 파일(`src/data/`).
  - 코드·설정·스키마·문서가 하나라도 섞인 커밋은 예외가 아니다(지금처럼 작업용 브랜치에서 하고 머지한다).
  - 공개(8단계 완료) 뒤부터 적용한다. 그 전의 콘텐츠 변경(8단계의 샘플 교체 등)은 단계 작업이므로 작업용 브랜치에서 한다.
  - 프로필의 활동명이나 한 줄 소개를 바꾸면 OG 이미지(원본은 `docs/stages/7-seo/`)도 다시 만들어야 하므로, 그 변경은 예외가 아니라 작업용 브랜치에서 한다. 프로필만 main에 push하면 빌드 결과 검사가 실패해 배포되지 않는다(7단계, [design.md](../design.md#메타-태그)).
  - push 전에 가능하면 `pnpm verify`를 돌린다. 웹에서 고쳐 로컬 확인을 못 하면 CI가 검증을 맡고, 실패하면 고침 커밋을 다시 push한다.
- 고친 문서: CLAUDE.md 작업 규칙(예외 추가), 개요의 "성공의 모습"(main에 push, 이 문서 링크)과 범위(검증 실패 시 배포하지 않음). 워크플로는 이미 main push에서 배포하므로 고치지 않았다. plan.md의 진행 방식(단계 작업과 완료 표시는 브랜치에서)은 콘텐츠 커밋이 아니므로 그대로 맞다.

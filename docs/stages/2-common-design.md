# 2단계: 공통 설계

목적과 끝난 상태는 [진행 계획](../plan.md)의 2단계를 따른다. 이 문서는 선택지 비교와 결정 이유를 담고, 확정된 설계는 [design.md](../design.md)에 적는다.

- 상태: 완료(2026-10-20, 사용자 검토 통과)
- 한 단계에서만 쓰는 세부(로더 구성, 이미지 넣는 방식, 화면 디자인 값 등)는 해당 단계에서 정한다.

## 1. 페이지 구성

필요한 페이지는 [개요](../project_overview.md)의 범위에서 나온다.

- 홈, 포트폴리오, 소개(프로필), 글 목록, 글 보기
- 그 밖에 404 페이지를 둔다. GitHub Pages는 `404.html`이 있으면 없는 주소에서 그 페이지를 보여 주므로, 사이트의 공통 레이아웃을 쓴 안내 페이지로 방문자를 사이트 안에 머물게 한다.

처음 추천안은 "홈 = 프로필 + 포트폴리오 한 페이지"였으나, 검토에서 사용자가 다음처럼 바꿨다(아래 "결정" 참고).

- 홈(`/`): 최근 포트폴리오 3개와 최근 글 3개
- 포트폴리오(`/portfolio/`): 별도 페이지
- 소개(`/about/`): 프로필

이에 따라 정한 세부:

- 홈 맨 위의 한 줄 소개: 홈에 프로필 전체는 두지 않되, 처음 온 방문자가 어떤 사람의 사이트인지 알 수 있게 `intro` 한 줄을 보여 준다. 이름은 헤더의 사이트 이름과 겹치므로 넣지 않는다.
- "최근 포트폴리오"의 기준 후보:
  - 파일 앞에서부터 3개(새 항목을 파일 맨 위에 적는다)
    - 장점: 개요의 "적은 순서대로 표시, 별도 순서 값 없음" 원칙을 그대로 지킨다. 홈과 포트폴리오 페이지의 순서가 같다.
    - 단점: 새 항목을 맨 위에 적는다는 것을 지켜야 한다.
  - 날짜 필드를 추가해 최신순
    - 장점: 파일 순서와 상관없이 정확하다.
    - 단점: 항목마다 날짜를 채워야 해 개요의 "관리할 것을 늘리지 않는다" 원칙과 어긋난다.
  - 추천: 파일 앞에서부터 3개.
- 개수가 3개보다 적으면 있는 만큼 보여 주고, 0개면 그 영역을 숨긴다(빈 영역이 보이지 않게).
- 포트폴리오 카드와 글 목록 항목은 홈과 전체 목록이 같이 쓴다(공통 컴포넌트, [design.md](../design.md#내비게이션과-공통-레이아웃-구성)).

글 목록의 페이지 나누기: 지금은 하지 않는다. 한 페이지에 모든 글을 보여 준다. 글이 많아져(예: 50개 이상) 필요해지면 `/blog/page/2/` 같은 주소를 추가하면 되고, 기존 `/blog/`와 글 주소는 바뀌지 않는다.

## 2. URL 구조

저장소가 사용자 사이트(`mivomad33.github.io`)라서 기본 주소와 도메인 연결 뒤 모두 루트에서 시작한다. 따라서 아래 경로는 도메인 연결 전후로 같다.

글 주소 후보:

- `/blog/<slug>/`(slug = md 파일 이름)
  - 장점: 짧고 읽기 쉽다. 파일 이름이 곧 주소라 따로 관리할 값이 없다.
  - 단점: 파일 이름을 바꾸면 주소가 바뀐다(공개 뒤에는 파일 이름을 바꾸지 않는다는 규칙으로 막는다).
- `/blog/<연>/<월>/<slug>/`
  - 장점: 같은 slug를 다른 해에 다시 쓸 수 있다.
  - 단점: 주소가 길고, 날짜를 고치면 주소가 바뀐다. 이 사이트의 글 양에서는 slug 충돌이 드물다.
- 한글 slug(`/blog/첫-글/`)
  - 장점: 제목과 주소가 같아 보인다.
  - 단점: 공유할 때 주소가 `%EC%B2%AB...`처럼 인코딩돼 보이고, 도구마다 처리가 달라 문제가 생기기 쉽다.

추천: `/blog/<slug>/`, slug는 영문 소문자·숫자·하이픈만 쓴다.

끝 슬래시 후보:

- 항상 붙인다(`/blog/`, `/blog/first-post/`)
  - 장점: GitHub Pages는 폴더의 `index.html`로 페이지를 내보내고, 슬래시 없는 주소는 슬래시 붙은 주소로 리다이렉트한다. 처음부터 슬래시를 붙인 주소만 쓰면 리다이렉트가 없고, 검색 엔진에 한 가지 주소만 알려진다.
  - 단점: 없음(링크를 쓸 때 슬래시를 빠뜨리지 않아야 하는데, Astro의 `trailingSlash: 'always'` 설정이 개발 중에 잘못된 링크를 드러낸다).
- 붙이지 않는다(`/blog`)
  - 단점: GitHub Pages의 기본 동작과 맞지 않아 리다이렉트가 생긴다.

추천: 항상 붙인다.

## 3. 내비게이션

- 헤더: 사이트 이름(홈 링크)과 메뉴 "포트폴리오", "블로그", "소개". 페이지마다 메뉴가 하나씩 있어 어느 페이지에서든 바로 간다. 순서는 방문자가 많이 찾을 것부터 둔다. 현재 위치가 메뉴에 표시된다.
- 푸터: 저작권 표시와 연락처(이메일, 프로필 `links`). 프로필 데이터 파일에서 가져와 같은 값을 두 곳에 적지 않는다.

글 보기 페이지의 이전·다음 글 링크와 "목록으로" 링크는 처음에는 두지 않는 것으로 추천했으나, 검토에서 사용자가 이전·다음 글 링크를 넣기로 했다(아래 "결정" 참고). "목록으로"는 헤더의 "블로그"가 같은 역할이라 두지 않는다.

## 4. 데이터 파일 형식

### 형식(JSON/YAML)

- YAML
  - 장점: 따옴표·쉼표가 적어 직접 고치기 쉽고, 여러 줄 설명과 주석을 쓸 수 있다. 데이터 파일은 사용자가 손으로 고치는 파일이다.
  - 단점: 들여쓰기를 틀리면 의도와 다르게 읽힌다(스키마 검증으로 빌드가 실패하므로 배포되지는 않는다).
- JSON
  - 장점: 해석이 엄격하고 별도 처리 없이 불러올 수 있다.
  - 단점: 직접 고치기 번거롭고 주석을 쓸 수 없다.

추천: YAML.

### 파일 나누기

- 프로필(`profile.yaml`)과 포트폴리오(`portfolio.yaml`)를 나눈다
  - 장점: 파일마다 맡는 내용이 분명하다. 포트폴리오는 목록 하나라 파일 자체가 배열이 되어 단순하다.
- 한 파일에 모두 넣는다
  - 장점: 고칠 파일이 하나다.
  - 단점: 성격이 다른 값(단일 프로필, 항목 목록)이 섞인다.

추천: 나눈다.

### 필드

개요의 원칙(필요한 것만 두고 필요해지면 추가)에 따라 최소로 정한다. 필드 이름은 영어로 쓴다(코드에서 그대로 쓰기 때문이다).

- 링크 형식은 프로필과 포트폴리오가 같은 것을 쓴다(`label`, `url`). 개요의 "링크명, 링크 주소"에 해당한다.
- 프로필의 "홈페이지(mivomad33.dev)"는 이 사이트 자체라 필드로 두지 않는다.
- 블로그 글의 `description`은 필수로 한다. 글 목록의 요약과 검색 결과 설명(7단계의 메타 설명)에 함께 쓰여, 없으면 둘 다 비게 되기 때문이다.
- 수정일, 초안 여부, 태그는 지금 두지 않는다. 태그는 개요에서 범위 밖이고, 초안은 사용자가 필요 없다고 정했다. 수정일은 검토에서 선택 필드 `updated`로 넣기로 했다(아래 "결정" 참고).

### 읽는 방법

콘텐츠 컬렉션 스키마로 검증하고, 지켜야 할 요구와 구현 방향은 [design.md](../design.md#데이터-파일-형식)에 적었다. 구체적인 로더 구성은 Astro 기본 로더의 동작을 확인해야 해서 5·6단계에서 정한다.

## 5. 디렉터리 구조

Astro의 기본 구조를 그대로 따른다. AI와 사람 모두 공식 문서와 같은 위치에서 파일을 찾을 수 있게 하기 위해서다. `src/lib/`만 추가한다(여러 페이지가 쓰는 로직을 모으는 곳, 아래 코드 규칙 참고).

## 6. 코드 규칙

정하는 기준: AI가 만든 코드가 단계마다 다르게 구현되지 않게 하는 규칙만 둔다. lint·포맷터가 자동으로 잡는 것은 규칙으로 적지 않는다.

스타일 값 규칙 후보:

- 색·글꼴·간격은 `@theme`에 정의한 값만 쓰고, 마크업에 임의 값(`text-[13px]`, `#333`)을 쓰지 않는다
  - 장점: 3단계에서 정한 값이 모든 화면에 일관되게 적용되고, 바꿀 때 한 곳만 고치면 된다.
  - 단점: 한 번만 쓰는 값도 테마에 넣거나 기존 값 중에서 골라야 한다.
- 제한하지 않는다
  - 단점: 화면마다 비슷하지만 다른 값이 쌓인다.

추천: 테마 값만 쓴다.

반복되는 클래스 묶음: `@apply`로 CSS 클래스를 만들지 않고 컴포넌트로 뽑는다. Tailwind 공식 권장 방식이고, 스타일과 마크업이 한 곳에 있어 고치기 쉽다.

클라이언트 JS: 기본으로 쓰지 않는다. 정적 사이트이고 상호작용이 거의 없어, 방문자에게 JS를 보내지 않는 Astro의 기본 출력을 유지한다. UI 프레임워크(React 등)도 넣지 않는다.

## 7. 테스트 전략

[plan.md](../plan.md)의 기본(빌드 시점 검증은 필수, 단위 테스트와 화면 비교 테스트는 지금 하지 않음)을 따르고, 1단계에서 정한 도구에 맞춰 구체화한다.

- 단위 테스트를 하지 않아도 되는 이유: 로직이 글 정렬, 날짜 표시 정도라 화면에서 바로 확인되고, 데이터 형식은 스키마가 빌드에서 막는다.
- 화면 비교 테스트를 하지 않는 이유: 화면이 적고, 디자인을 고칠 때마다 기준 이미지를 갱신해야 해서 관리 부담이 크다.
- 다시 검토할 때: `src/lib/`의 로직이 화면만 보고 확인하기 어려울 만큼 복잡해지면 그 부분에 단위 테스트(Vitest)를 추가한다.

## 결정

확정된 설계는 [design.md](../design.md)에 있다.

- 2026-10-20(검토 중 변경): 사용자가 페이지 구성을 바꿨다. 홈에 프로필을 두는 것보다 최근 포트폴리오와 최근 글을 보여 주는 편이 낫고, 포트폴리오는 별도 페이지, 프로필은 `/about/`에 둔다. 이 변경으로 개요의 범위와 plan.md의 3·5·6단계 문구도 고쳤다.
- 2026-10-20(검토 반영): 별도 세션 검토에서 나온 지적을 사용자가 모두 반영하기로 했다.
  - 글과 데이터 파일은 Prettier 검사에서 뺀다. 포맷 차이로 글 배포가 막히면 "md push로 자동 배포" 목표와 부딪히기 때문이다.
  - 사이트 이름은 프로필의 `name`을 쓴다. 같은 값을 두 곳에 두지 않기 위해서다.
  - 링크 `url`에 `/`로 시작하는 사이트 안 주소도 허용한다. 포트폴리오 항목에서 관련 글로 연결할 수 있게 하기 위해서다.
  - 날짜는 UTC 기준으로 표시하고, 데이터 로더의 `id`·순서 처리 방향을 design.md에 적었다.
  - URL(`/portfolio/`, `/about/`, `/blog/<영문-slug>/`), 메뉴("포트폴리오, 블로그, 소개"), "새 포트폴리오 항목은 파일 맨 위에 적는다"는 운영 규칙을 확정했다.
- 2026-10-20(2차 검토 반영): 두 번째 별도 세션 검토의 지적을 사용자가 추천대로 반영하기로 했다.
  - 홈 한 줄 소개는 `intro`만 보여 준다. 이름이 헤더와 겹쳐 두 번 보이기 때문이다.
  - 푸터는 GitHub만이 아니라 프로필 `links` 전체를 보여 준다. 데이터에 GitHub 전용 필드가 없기 때문이다.
  - 링크 `url`에서 `//`로 시작하는 주소를 막고, slug 형식이 틀리면 빌드가 실패하게 한다(방법은 6단계).
  - 글과 데이터 파일에 더해 `docs/`, `CLAUDE.md`도 Prettier 검사에서 뺀다. 배포되지 않는 문서 때문에 배포가 막히지 않게 하기 위해서다.
  - 날짜 표시 형식은 3단계, 도메인 연결 때의 `site` 설정 변경은 8단계의 끝난 상태에 넣었다.
- 2026-10-20(검토 중 변경): 글 보기 본문 아래에 이전·다음 글 링크를 둔다. 글 제목을 함께 보여 줘 누르기 전에 내용을 짐작할 수 있게 하기 위해서다. "목록으로" 링크는 필요 없다고 사용자가 정했다.
- 2026-10-20(검토 중 결정): 초안(`draft`) 필드는 두지 않는다. 사용자가 필요 없다고 정했다.
- 2026-10-20(검토 중 결정): 블로그 글에 선택 필드 `updated`(수정일)를 둔다. 개발 글은 내용이 낡기 쉬워 수정 시점을 독자에게 보여 주는 의미가 있고, 7단계에서 검색 엔진에 수정 시점을 알리는 데도 쓰기 때문이다.
- 2026-10-20: 위에서 바꾸거나 따로 정한 것 외의 항목(URL 형식, YAML, 파일 나누기, 디렉터리 구조, 코드 규칙, 테스트 전략 등)은 추천안대로 채택했다. 사용자 검토를 통과했다.

# 진행 계획

목표, 원칙, 범위는 [프로젝트 개요](project_overview.md)를 따른다. 이 문서는 가장 큰 단위의 단계 구성과 진행 상태만 담는다.
단계별 세부 기획·설계는 단계를 시작할 때 `docs/stages/<번호>-<이름>.md`에 작성한다.

## 진행 방식

- 단계마다 작업용 브랜치에서 작업하고, 파일을 고치면 바로 커밋한다.
- 자동 검증(4단계 이후)이 있으면 Claude가 먼저 통과시킨 뒤 사용자 검토를 받는다.
- 단계의 끝난 상태에 도달하면 사용자가 검토한다(4단계 이후는 로컬 빌드 미리보기로 확인한다. 배포는 main 머지 뒤에 일어나기 때문이다). 통과하면 사용자에게 확인을 받고 main에 squash merge한 뒤 브랜치를 삭제한다.
- 배포에 관한 끝난 상태(4·8단계)는 머지 뒤 실제 배포로 확인하고, 확인되면 완료로 표시한다. 완료 표시 같은 문서 갱신과 문제 수정은 모두 새 작업용 브랜치에서 하고 머지한다(main에 직접 커밋하지 않는다는 규칙을 지키기 위해서다).
- 검토를 통과하면 이 문서의 진행 상태와 개요의 "현재 상태"를 갱신하고 다음 단계로 넘어간다.
- 단계에서 정한 내용이 개요의 원칙이나 범위를 바꾸면 개요도 함께 고친다.

## 단계

1. 기술 스택 선정 — 상태: 완료(2026-10-20)
   - 목적: 이후 모든 코드의 기반이 될 기술을 정한다.
   - 끝난 상태: 다음 항목이 AI 주도 개발, 정적 빌드, GitHub Pages 배포, md 블로그, SEO 기준으로 비교·결정되고, 결정과 이유가 기록돼 있다. 비교 과정은 단계 파일에, 확정된 스택은 모든 단계가 따르므로 `docs/design.md`에 적는다.
     - 프레임워크(Astro, Next.js 등)
     - 스타일링 방식(순수 CSS, Tailwind 등)과 UI 컴포넌트 라이브러리 사용 여부
     - TypeScript 사용 여부, 패키지 매니저, lint·포맷터
     - md 처리 방식(코드 하이라이팅 포함)
     - 배포 방식(GitHub Actions 등), sitemap 등 SEO 도구
     - 검증 도구(타입 검사, lint, 데이터 형식 검증, E2E 도구 사용 여부)
     - 한 단계에서만 쓰는 세부(하이라이팅 테마 등)는 해당 단계에서 정한다.
   - 순서의 이유: 설계(디렉터리 구조, 데이터 파일 형식)와 구현, 배포 방식이 모두 기술 선택에 따라 달라진다.
   - 세부: [stages/1-tech-stack.md](stages/1-tech-stack.md)

2. 공통 설계 — 상태: 완료(2026-10-20)
   - 목적: 여러 단계가 같이 쓰는 구조와 규칙을 구현 전에 정해, 단계마다 다르게 구현되지 않게 한다.
   - 끝난 상태: 다음 항목이 `docs/design.md`에 정리되고 사용자 검토를 통과했다.
     - 페이지 구성, URL 구조(GitHub Pages 기준 경로 포함), 내비게이션(공개 후 URL을 바꾸면 검색 노출이 나빠지므로 미리 정한다)
     - 데이터 파일 형식(프로필, 포트폴리오, 블로그 글 정보)
     - 디렉터리 구조, 코드 규칙
     - 테스트 전략(무엇을 어느 수준에서 검증할지). 빌드 시점 검증(타입 검사, lint, 데이터 형식 검증)은 필수로 하고, 단위 테스트와 화면 비교 테스트는 로직이 적고 관리 부담이 커서 지금은 하지 않는 것을 기본으로 한다.
   - 순서의 이유: 1단계에서 정한 기술에 맞춰 설계하며, 3단계 시안이 담을 화면 구성과 4단계 이후 구현이 이 설계를 따른다.
   - 세부: [stages/2-common-design.md](stages/2-common-design.md)

3. UI 디자인 시안 — 상태: 완료(2026-10-20)
   - 목적: 구현 전에 사이트의 시각적 방향을 정해, 단계마다 색·글꼴·간격을 따로 정하거나 나중에 전체를 다시 손보지 않게 한다.
   - 끝난 상태: 주요 화면(홈, 포트폴리오, 소개, 글 목록, 글 보기)의 방향이 다른 HTML 시안 2~3개 중 하나를 사용자가 골랐고, 색·글꼴·간격 등 기본 값과 날짜 표시 형식이 `docs/design.md`의 공통 UI로 확정돼 있다.
   - 순서의 이유: 2단계에서 정한 페이지 구성을 바탕으로 시안을 만들며, 4단계의 공통 레이아웃이 이 결과를 따른다. 2단계와 나눈 것은 검토 방식(문서 검토와 시안 선택)이 다르기 때문이다.
   - 세부: [stages/3-ui-design.md](stages/3-ui-design.md)
   - 하위 단계:
     1. 시안 제작 — 상태: 완료(2026-10-20)
        - 할 일: 단계 파일에 미니멀 안에서 방향이 다른 시안 2~3개의 콘셉트(색, 글꼴, 간격, 배치)를 적고, 시안마다 HTML 파일 하나(`docs/stages/3-ui-design/`)에 주요 화면 5개를 design.md의 페이지 구성대로 만든다.
          - 예시 데이터: design.md의 예시는 화면을 확인하기에 부족하므로 시안용으로 따로 만든다(포트폴리오 3개 이상, 글 4개 이상, 줄바꿈되는 긴 제목·설명, 제목 단계·목록·인용·코드 블록·링크가 든 글 본문).
          - 2단계에서 표시 여부만 정하고 모양은 정하지 않은 것(헤더의 현재 메뉴 표시, 글 보기의 이전·다음 글 링크)과 날짜 표시를 넣는다.
          - 색·글꼴·간격·글자 크기는 `@theme` 이름 형식의 CSS 변수(`--color-*`, `--font-*` 등)로만 정의해 쓴다. 하위 단계 3(공통 UI 확정)에서 값을 그대로 옮길 수 있고, 값의 종류가 처음부터 적게 유지되기 때문이다.
        - 완료 확인: 시안 파일을 브라우저로 열면 5개 화면이 모두 보이고, 데스크톱과 모바일(375px) 폭에서 가로 스크롤 없이 표시된다.
     2. 시안 선택과 다듬기 — 상태: 완료(2026-10-20)
        - 할 일: 사용자가 시안 하나를 고르거나(다른 시안의 요소를 섞는 것 포함) 고칠 점을 정하고, Claude가 고른 시안에 반영한다.
        - 완료 확인: 사용자가 다듬은 시안을 최종안으로 승인한다.
     3. 공통 UI 확정 — 상태: 완료(2026-10-20)
        - 할 일: 최종안의 색·글꼴(웹 폰트 사용 여부와 불러오는 방법 포함)·간격·글자 크기 등 기본 값, 날짜 표시 형식, 헤더의 현재 메뉴 표시와 이전·다음 글 링크 모양, 글 본문(md) 요소의 스타일을 `@theme`에 옮길 수 있는 값으로 `docs/design.md`의 공통 UI에 적고, 비교와 결정 이유를 단계 파일에 적는다.
          - 코드 블록은 글꼴·여백·모서리 같은 틀만 정하고, 배경색과 문법 색은 6단계에서 정하는 하이라이팅 테마를 따른다(Shiki 테마가 배경색까지 정하므로 두 단계가 같은 값을 정하지 않게 하기 위해서다).
        - 완료 확인: design.md 공통 UI에 끝난 상태의 항목이 모두 있고, 사용자 검토를 통과한다.

4. 기반 구축과 배포 파이프라인 — 상태: 완료(2026-10-20)
   - 목적: 이후 단계의 결과가 머지될 때마다 자동으로 배포되게 해, 배포 문제를 일찍 발견한다.
   - 끝난 상태: 설계대로 프로젝트 골격과 공통 레이아웃(헤더·푸터 등)이 만들어져 있고, main에 push하면 검증(타입 검사, lint 등)과 빌드를 거쳐 GitHub Pages(기본 주소)로 자동 배포되며, 검증이나 빌드가 실패하면 배포되지 않는다. 공개 전이므로 검색 엔진 수집은 막혀 있다(robots.txt Disallow, noindex 등).
   - 순서의 이유: 1~3단계의 결정을 코드로 옮기는 첫 단계이며, 배포를 먼저 갖춰 두면 5·6단계 결과가 머지마다 실제 환경에 반영돼 배포 문제가 마지막에 몰리지 않는다.
   - 세부: [stages/4-foundation.md](stages/4-foundation.md)
   - 하위 단계:
     1. 프로젝트 골격과 검증 명령 — 상태: 완료(2026-10-20)
        - 할 일: design.md의 기술 스택대로 Astro 프로젝트를 만들고(Tailwind, TypeScript strict, ESLint, Prettier, `trailingSlash: 'always'`, `site` 기본 주소), 로컬과 CI가 같이 쓸 검증 명령(타입 검사, lint, 포맷 검사, 빌드)을 `package.json` 스크립트로 구성한다. 검사만 하는 명령(타입·lint·포맷), 빌드 명령, 둘을 합친 명령(로컬 확인용)으로 나눈다. CI가 검사와 빌드를 다른 작업에서 부를 때 빌드가 두 번 실행되지 않게 하기 위해서다. Node 버전을 로컬과 CI가 같이 읽을 수 있는 곳에, pnpm 버전을 `package.json`의 `packageManager`에 고정하고(CI의 pnpm 설치가 이 값을 읽는다), `.prettierignore`를 테스트 전략대로 만든다. 고른 패키지 버전과 명령 구성, 그 이유를 단계 파일에 적는다.
        - 완료 확인: 새로 클론한 상태와 같게 `pnpm install` 뒤 검증 명령 하나로 타입 검사·lint·포맷 검사·빌드가 모두 통과하고, 일부러 타입 오류, lint 오류, 포맷 오류를 하나씩 넣으면 그때마다 그 명령이 실패한다.
     2. 공통 레이아웃 — 상태: 완료(2026-10-20)
        - 할 일: design.md 공통 UI의 디자인 값을 `src/styles/global.css`의 `@theme`에 옮기고(Tailwind 기본 값을 지울 범위, 글자 크기별 줄 간격 포함), 웹 폰트를 npm 패키지로 불러온다. `BaseLayout`(문서 머리, 헤더, 푸터, 현재 메뉴 표시)과 `404` 페이지, 메뉴 확인용 빈 페이지(`/`, `/portfolio/`, `/blog/`, `/about/`, 내용은 5·6단계에서 채운다)를 만든다. 공개 전 수집 차단(robots.txt Disallow, 모든 페이지 noindex)과 8단계에서 푸는 방법을 정해 넣는다. 정한 내용은 단계 파일에, 여러 단계가 따를 것은 design.md에 적는다.
          - 헤더·푸터가 프로필 데이터(`name`, `email`, `links`)를 쓰므로 `src/data/profile.yaml`과 그 스키마는 이 하위 단계에서 만든다(프로필 파일 로더 동작 확인도 여기서 한다). design.md의 "로더 세부는 5단계(프로필·포트폴리오)" 문구도 함께 고친다. 포트폴리오는 5단계에 남긴다.
        - 완료 확인: 검증 명령이 통과하고(`.astro`에 순서가 틀린 Tailwind 클래스를 넣으면 포맷 검사가 실패하는 것 포함), 빌드 미리보기에서 모든 페이지의 헤더·푸터가 [c-mono.html](stages/3-ui-design/c-mono.html)과 같은 모양으로 보이고 현재 메뉴가 맞게 표시되며, 없는 주소에서 404가 나온다. 데스크톱과 모바일(375px)에서 가로 스크롤이 없고, 글꼴을 외부 서버가 아닌 사이트에서 불러오며, 빌드 결과의 모든 페이지에 noindex가 있고 robots.txt가 전체를 막는다.
     3. 배포 파이프라인 — 상태: 완료(2026-10-20)
        - 할 일: GitHub 저장소 `mivomad33/mivomad33.github.io`(Public, 빈 저장소)를 만들고 Pages 배포 방식을 GitHub Actions로 설정한다(완료 2026-10-20, 원격 `origin` 연결과 push 권한 확인까지). Claude가 `.github/workflows/`에 검증 → 빌드 → 배포 워크플로를 만든다. 세 작업을 `needs`로 한 줄로 잇고(검증 작업은 하위 단계 1의 검사 명령을, 빌드 작업은 빌드 명령을 부른다), 배포 작업만 main push 조건을 둔다(다른 브랜치 push에서는 검증·빌드만 한다).
          - 원격에 올릴 때는 작업 브랜치보다 main을 먼저 push한다. 빈 저장소에 처음 올린 브랜치가 기본 브랜치가 되고, Pages 배포 환경은 기본적으로 기본 브랜치에서만 배포를 허용하기 때문이다. 이미 있는 main을 그대로 올리는 것이라 main에 직접 커밋하는 것은 아니다. 올린 뒤 기본 브랜치가 main인지 확인한다.
        - 완료 확인: 워크플로에서 배포 작업이 검증·빌드와 `needs`로 이어져 있고, 작업 브랜치에 일부러 검증 실패를 넣어 push하면 검증이 실패하고 다음 작업(빌드)이 skipped된다(작업 브랜치에서는 원래 배포가 실행되지 않으므로, 실패가 다음 작업을 막는 것을 이렇게 확인한다). main 머지 뒤 push로 `https://mivomad33.github.io/`에 사이트가 배포된다(배포 확인은 진행 방식대로 머지 뒤에 한다).

5. 홈·포트폴리오·소개 페이지 — 상태: 완료(2026-10-20)

     1. 포트폴리오 데이터와 포트폴리오 페이지 — 상태: 완료(2026-10-20)
        - 할 일: design.md의 형식대로 `src/data/portfolio.yaml`(샘플 3개 이상. 링크 없는 항목, 링크가 여러 개인 항목, 줄바꿈되는 긴 명칭·설명 포함)과 스키마(`strictObject`, 링크는 `linkSchema`)를 만든다. 배열의 위치로 `id`를 만들고 그 순서로 정렬하며, 읽기 오류와 배열이 아닌 파일에서 빌드를 멈추는 로더를 만든다(프로필 로더 `yaml-object-loader.ts`와 겹치는 부분은 공통으로 뽑는다). 포트폴리오를 파일 순서대로 가져오는 함수(홈의 최근 3개를 가져오는 함수 포함. 페이지가 데이터를 직접 가공하지 않는다는 코드 규칙 때문이다)를 `src/lib/`에, 포트폴리오 카드를 `src/components/`에 만들고(홈과 같이 쓴다), `/portfolio/`에 모든 항목을 카드로 보여 준다. 로더 동작과 결정 이유는 단계 파일에, 여러 단계가 따를 것은 design.md에 적는다("포트폴리오 로더는 5단계" 문구 포함).
        - 완료 확인: 검증 명령(`pnpm verify`)이 통과하고, 빌드 미리보기의 `/portfolio/`에 모든 항목이 파일 순서대로 [c-mono.html](stages/3-ui-design/c-mono.html)과 같은 모양의 카드로 보인다(데스크톱과 모바일 375px에서 가로 스크롤 없음). 한 번 빌드에 성공한 뒤(이전 빌드의 데이터가 남은 상태) 일부러 필수 항목 빠뜨리기, 정해지지 않은 키, 형식이 틀린 링크, YAML 문법 오류, 배열이 아닌 파일을 하나씩 넣으면 그때마다 빌드가 실패한다(4단계에서 기본 로더가 이 상태에서만 오류를 숨긴 것을 확인했기 때문이다). 로더 공통 부분을 뽑은 뒤에도 `profile.yaml`에 YAML 문법 오류를 넣으면 빌드가 실패한다. 파일에서 항목 순서를 바꾸면 화면 순서도 바뀌고, 빈 배열(`[]`)이면 빌드가 통과하며 안내 문구가 보인다.
     2. 소개 페이지와 홈 — 상태: 완료(2026-10-20)
        - 할 일: `/about/`에 프로필(활동명, 소개, 이메일, 링크)을 시안 모양대로 보여 준다. 홈의 한 줄 소개 아래에 최근 포트폴리오(앞에서 3개, 하위 단계 1의 카드)와 전체 목록 링크를 둔다. 홈의 영역 제목(`## ` + 제목 + "전체 보기 →")은 6단계의 최근 글 영역도 쓰므로 공통 컴포넌트로 만든다. 항목이 0개면 그 영역을 숨긴다.
        - 완료 확인: 검증 명령이 통과하고, 빌드 미리보기에서 소개 페이지와 홈이 시안과 같은 모양으로 보이며(데스크톱·모바일에서 가로 스크롤 없음), 프로필·포트폴리오 데이터 파일을 고치면 소개 페이지·포트폴리오 페이지·홈에 반영된다. 홈에서 포트폴리오가 3개보다 많으면 앞의 3개만, 적으면 있는 만큼 보이고, 빈 배열이면 영역이 사라진다.

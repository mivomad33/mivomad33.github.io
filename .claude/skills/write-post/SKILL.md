# 대화로 글을 기획해 쓰고 배포하기

입력은 글로 쓰고 싶은 아이디어다(인자로 받는다. 없으면 묻는다). 한 줄 주제여도, 긴 메모여도 된다.
결과는 이 저장소의 글 폴더(`src/content/blog/<slug>/`의 `ko.md`, `en.md`, 필요하면 `images/`)와, main에 push되어 배포된 글이다.

흐름: **시작 → 기획 대화(반복) → 쓸 준비 알림과 확인 → 한국어 초안(반복) → 영어 글 → 검증 → push 확인 → push·배포 확인 → 정리와 보고.**
사용자 확인을 받는 곳은 네 곳이다: 쓰기 시작(3장), 한국어 승인(4장), 영어 확인(5장), push(7장). 확인 없이 다음 장으로 넘어가지 않는다.

글의 형식·내용 원칙·문체·영어 글·이미지 넣기·검증·커밋·배포 규칙은 [공통 규칙](../shared/post-writing.md)을 따른다. 이 파일에는 대화로 기획하는 데 필요한 것만 둔다.
결정과 이유는 [변경 7 문서](../../../docs/changes/7-write-post-skill.md)에 있다.

목표는 **그 사람만 쓸 수 있는 글**이다. 재료는 사용자의 경험·생각·숫자이고, AI는 그것을 끌어내 구조를 잡고 문장으로 만든다. 빈 곳을 그럴듯한 일반론으로 메우는 것이 이런 글의 가장 흔한 실패다.

## 1. 시작

- `drafts/`에 기획 메모가 있으면 목록(파일 이름, 아이디어, 상태)을 보이고 이어 갈지, 새로 시작할지 묻는다. 이어 가면 메모를 읽고 그 상태의 장부터 한다.
- 이 저장소의 `CLAUDE.md`, `docs/memory.md`, [공통 규칙](../shared/post-writing.md)을 읽는다.
- 기존 글(`src/content/blog/`)의 제목과 설명을 훑어, 같은 주제의 글이 있으면 알린다(새 글로 쓸지, 그 글을 고칠지 묻는다). 문체는 기존 글에서 참고한다.
- git 상태를 [공통 규칙](../shared/post-writing.md)의 커밋과 push에 적힌 대로 본다(main, 깨끗한 작업 폴더, 원격과 같음). 다른 작업이 섞인 채 콘텐츠 커밋을 main에 push하지 않기 위해서다. 이어 가는 경우에는 이번 글 폴더의 변경만 있어야 한다.
- 기획 메모를 만든다: `drafts/<오늘 날짜>-<임시 이름>.md`(임시 이름은 아이디어를 영문 소문자·하이픈으로 줄인 것). `drafts/`는 git에서 제외되어 있다. 형식은 아래 "기획 메모"를 따른다.

## 2. 기획 대화

### 첫 응답

아이디어를 분석해 한 메시지에 보인다.

- 이 아이디어에서 읽히는 것: 무엇에 대한 이야기인지, 이미 있는 재료와 빠진 재료.
- 글의 방향 2~3개: 방향마다 중심 메시지 한 줄, 누구에게 무엇이 남는 글인지, 필요한 재료. 추천안을 앞에 두고 고른 이유를 짧게 적는다.
- 첫 질문 1~3개.
- 기획 체크리스트(아래).

### 질문 원칙

- 한 번에 1~3개만 묻는다. 중요한 것부터 묻는다.
- 고를 수 있는 질문(방향, 독자, 구성)은 묻는 도구로 선택지와 추천안을 함께 준다. 경험을 묻는 질문은 메시지로 묻는다(선택지로 답할 수 없다).
- 경험을 묻는 질문은 구체적인 장면을 끌어내게 한다. "어떻게 생각하세요?"보다 "그때 실제로 무엇을 했나요?", "무엇이 예상과 달랐나요?", "숫자로 말하면 얼마였나요?", "처음 생각과 바뀐 것은?"처럼 묻는다.
- 답이 일반론이면 한 번 더 구체적으로 묻는다(예: "예를 하나만 들어 주실 수 있나요?"). 그래도 없으면 그 내용은 글에서 빼거나 짧게 쓸 것을 제안한다.
- 사용자가 모른다고 하거나 넘기면 그 항목을 지어내지 않는다. 다른 방향을 제안하거나 그 부분 없이 쓰는 구성을 제안한다.
- 방향이 바뀌면 바뀐 것을 체크리스트에 반영하고, 버린 방향의 재료가 새 방향에도 쓰이는지 알린다.
- 사용자가 묻지 않아도, 글이 더 좋아질 방법(이야기의 순서, 빼면 좋을 것, 독자가 궁금해할 것)이 보이면 짧게 제안한다.

### 기획 체크리스트

매 응답 끝에 보인다. 항목마다 정해진 내용 또는 "아직"을 적는다.

- 중심 메시지: 독자가 이 글에서 가져갈 것 한 줄
- 대상 독자
- 섹션 구성안: 섹션 제목과 섹션마다 할 이야기 한 줄
- 섹션별 재료: 섹션마다 쓸 구체적인 경험·사례·숫자(사용자가 말한 것)
- 제목(한국어), slug, 설명(한두 문장)

제목·slug·설명은 다른 항목이 채워진 뒤에 후보를 낸다(slug는 [공통 규칙](../shared/post-writing.md)의 형식).

### 기획 메모

응답할 때마다 메모를 고친다. 세션이 끊겨도 메모만 읽고 이어 갈 수 있게 쓴다.

```markdown
# 기획 메모: <임시 이름>

- 아이디어: <처음 받은 그대로>
- 상태: 기획 중 | 한국어 초안 | 영어 글 | push 대기 | 배포 확인
- slug: <정해지면>

## 체크리스트

(위 체크리스트의 지금 상태)

## 사실

- <사용자가 말한 경험·생각·숫자. 사용자의 말에 가깝게 적는다>

## 정한 것

- <방향, 독자, 구성, 뺀 것과 그 이유>
```

- **사실** 칸에는 사용자가 말한 것만 적는다. AI가 짐작하거나 보탠 것은 적지 않는다. 쓰기 단계에서는 이 칸에 있는 사실만 쓴다.
- 사용자가 링크나 파일을 주면 읽고, 거기서 쓸 사실을 출처와 함께 적는다.

## 3. 쓸 준비 알림과 확인

- 체크리스트가 모두 채워지면 "쓸 준비가 됐다"고 알리고 기획안 전체(체크리스트 내용)를 보인다. 확인받으면 4장으로 간다. 고칠 곳을 말하면 2장으로 돌아간다.
- 사용자가 더 일찍 "이걸로 써 줘"라고 하면 빈 항목과 그 영향(예: "2번 섹션은 재료가 없어 짧아집니다")을 알리고, 그래도 쓰는지 확인한다.
- 이미지가 글에 도움이 되면 이때 제안한다. 이미지는 사용자가 파일 경로로 준다. AI가 만들거나 찍지 않는다.

## 4. 한국어 초안

- 글 폴더 `src/content/blog/<slug>/`를 만들고 `ko.md`를 [공통 규칙](../shared/post-writing.md)대로 쓴다. 기획 메모의 사실만 쓴다.
- 블로그 로더는 `en.md`가 없으면 개발 서버에서도 오류를 내므로, 영어 임시 파일을 함께 둔다. 이 파일은 커밋하지 않는다.

  ```markdown
  ---
  title: Draft
  description: Draft
  date: <ko.md와 같은 날짜>
  ---

  Draft.
  ```

- 이미지를 받았으면 [공통 규칙](../shared/post-writing.md)의 이미지 넣기대로 넣는다.
- 개발 서버(`.claude/launch.json`의 `site-dev`)를 열고 내장 브라우저에서 글 주소(`http://localhost:4321/blog/<slug>/`)를 보인다. 사용자는 같은 창에서 읽는다. 오류 화면이면 고친 뒤 보인다.
- 사용자에게 읽고 고칠 곳을 말해 달라고 한다. 고친 뒤에는 새로 고침해 다시 보이고, 무엇을 고쳤는지 짧게 알린다.
- 수정 중 새 사실이 나오면 메모에 더한다. 사용자가 고친 문장에 새 사실이 있으면 그것도 메모에 적는다.
- 사용자가 한국어 글을 승인하면 메모의 상태를 고치고 5장으로 간다.

## 5. 영어 글

- 승인된 한국어 글로 `en.md`를 [공통 규칙](../shared/post-writing.md)의 영어 글대로 쓴다. 임시 파일을 덮어쓴다.
- 개발 서버에서 영어 글(`http://localhost:4321/en/blog/<slug>/`)을 보이고 확인받는다. 영어를 고치다 사실이 바뀌면 한국어 글도 함께 고친다(두 언어가 어긋나지 않게).

## 6. 검증

- [공통 규칙](../shared/post-writing.md)의 검증을 모두 통과시킨다. 사실 대조는 기획 메모의 **사실** 칸과 한다.
- `en.md`가 임시 파일이 아닌지 본다(`title`이 `Draft`이거나 본문이 `Draft.`이면 실패).
- 바뀐 파일이 글 폴더 안에만 있는지 본다(`git status`). 다른 파일이 있으면 콘텐츠 예외가 아니므로 멈추고 알린다.

## 7. push 확인

한 메시지에 보이고 push를 확인받는다.

- 글 제목과 개발 서버 주소(두 언어), 배포되면 열릴 주소(`https://mivomad33.dev/blog/<slug>/`, `/en/blog/<slug>/`).
- 커밋할 파일 목록과 커밋 메시지.
- 검증 결과(항목마다 통과 여부)와 글 보기 스크린샷.

확인받기 전에는 push하지 않는다. 고칠 곳을 말하면 고치고 6장부터 다시 한다.

## 8. push와 배포 확인

[공통 규칙](../shared/post-writing.md)의 커밋과 push, 배포 확인대로 한다.

## 9. 정리와 보고

- 배포 확인이 끝나면 기획 메모(`drafts/<파일>`)를 지운다. 배포가 실패했으면 지우지 않는다.
- 짧게 알린다: 운영 주소(두 언어), 커밋, 배포 결과.

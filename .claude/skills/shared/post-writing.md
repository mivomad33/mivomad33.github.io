# 블로그 글 공통 규칙

`add-project`와 `write-post`가 함께 따르는 글쓰기·검증·커밋·배포 규칙이다. 스킬이 아니라 두 스킬이 참조하는 파일이다(`SKILL.md`가 없어 스킬로 잡히지 않는다).
두 스킬에 같은 규칙을 따로 두면 고칠 때 어긋나므로, 글에 관한 공통 규칙은 여기에만 둔다. 사실 메모를 어떻게 만드는지처럼 스킬마다 다른 것은 각 스킬에 둔다.

결정과 이유는 [변경 6](../../../docs/changes/6-add-project-skill.md), [변경 7](../../../docs/changes/7-write-post-skill.md) 문서에 있다.

## 1. 형식

- 폴더: `src/content/blog/<slug>/`. slug는 영문 소문자·숫자를 하이픈 하나로 이은 이름이다(예: `building-senseful`). 공개 뒤에는 주소가 바뀌지 않게 폴더 이름을 바꾸지 않으므로 사용자에게 확인받은 값을 쓴다.
- 폴더 안에는 `ko.md`, `en.md`, `images/`만 둔다. 다른 파일이 있거나 언어 파일이 하나라도 없으면 빌드(개발 서버 포함)가 실패한다.
- frontmatter: `title`, `description`, `date`(오늘, `YYYY-MM-DD`). 다른 키를 넣지 않는다. 제목에 `:`가 있으면 따옴표로 감싼다. 두 파일의 `date`는 같다.
- 형식의 기준은 `docs/design.md`의 데이터 파일 형식이다. 이 파일과 다르면 design.md를 따른다.

## 2. 내용

- **사실 메모에 있는 것만 쓴다.** 동기, 경험, 숫자, 비용, 결과를 지어내지 않는다. "빠르다", "정확하다" 대신 무엇을 했고 결과가 어땠는지 쓴다.
- 결정을 쓸 때는 **무엇을 정했는지, 왜, 무엇을 뺐는지**를 함께 쓴다. 처음 생각과 바꾼 이유가 있으면 그것이 가장 좋은 재료다.
- **이유도 사실이다.** 메모에 이유가 없는 결정은 결정만 쓴다. 그럴듯한 이유를 덧붙이지 않는다(시험 실행에서 가장 쉽게 생긴 실수다).
- 한계와 아직 확인하지 못한 것도 쓴다(예: Senseful 글의 "이 세트에 맞춰졌을 수 있습니다"). 과장하지 않는다.
- 흐름은 이야기에 맞게 정한다. 기존 글의 섹션 구성을 틀로 쓰지 않는다. 매번 같은 구성이면 글이 비슷해지기 때문이다.
- 빈 곳을 일반론으로 메우지 않는다. 사실이 적으면 글을 짧게 쓴다.

## 3. 문체

기존 글(`src/content/blog/building-senseful/`, `building-wonbook/`)과 같게 쓴다. 문체와 원칙을 참고하고 구성은 따라 하지 않는다.

- 합니다체, 1인칭("제가"는 꼭 필요할 때만). 문단은 짧게, 나열은 리스트로. 제목은 `##`까지만 쓴다(필요하면 `###`).
- 라이브러리·명령·식별자는 백틱으로 쓴다. 외부 링크는 마크다운 링크로 쓴다(새 탭 표시는 사이트가 붙인다). HTML `<a>`를 직접 쓰지 않는다.
- 길이는 본문 60~90줄 정도를 기준으로 하되, 사실이 적으면 짧게 쓴다. 늘리려고 일반론을 넣지 않는다.

## 4. 영어 글

- 섹션 구조, 사실, 숫자, 이미지, 링크는 한국어 글과 같다. 한쪽에만 있는 문장을 두지 않는다.
- 글자 그대로 옮기지 않고 자연스러운 영어로 쓴다. 한국 독자만 아는 맥락은 짧게 풀어 쓴다.
- `title`·`description`에 한글을 쓰지 않는다(빌드가 실패한다). 본문에서 한국어 화면 문구를 인용해야 하면 뜻을 영어로 쓰고 필요할 때만 원문을 괄호에 둔다.
- 대체 텍스트는 영어로 쓰고, 화면이 한국어면 그렇다고 적는다(예: `(in Korean)`).
- 사이트 안 링크는 영어 주소(`/en/...`)로 쓴다. 데이터 파일과 달리 글 본문의 사이트 안 링크는 자동으로 바뀌지 않는다.

## 5. 이미지 넣기

이미지를 어떻게 얻는지(직접 찍기, 사용자가 주기)는 스킬마다 다르다. 넣는 규칙은 같다.

- 크기: 가로 1600px 안팎, 파일 1MB 이하의 jpg나 png. 빌드가 webp로 줄이므로 따로 webp로 바꾸지 않는다. 크면 macOS의 `sips`(예: `sips -Z 1600 <파일>`)로 줄인다.
- 저장한 이미지는 **하나씩 열어 눈으로 확인한다**: 개인 데이터, 비밀 값, 개발 전용 표시, 잘린 화면이 없는지.
- 글 폴더의 `images/`에 두고 본문에 `![대체 텍스트](./images/<파일>)`로 넣는다. 대체 텍스트는 그 글의 언어로, 무엇이 보이는지 쓴다(빈 대체 텍스트는 빌드가 잡지 못하므로 직접 확인한다).

## 6. 검증

커밋하기 전에 모두 통과시킨다. 실패하면 고치고 다시 한다.

- `pnpm verify`(형식·타입·린트·빌드와 빌드 결과 검사).
- 사실 대조: 글의 숫자·이름·경험, **그리고 "~기 때문입니다" 같은 이유 문장**을 사실 메모와 하나씩 대조한다. 메모에 없으면 출처에서 다시 찾고, 없으면 지운다.
- 두 언어 대조: 두 글을 섹션마다 나란히 읽어 한쪽에만 있는 문장·숫자·링크가 없는지 본다.
- 링크: 외부 링크가 응답하는지(`curl -sI`) 본다.
- 화면: 개발 서버(`.claude/launch.json`의 `site-dev`)를 열고 두 언어에서 글 보기(이미지, 제목, 날짜, 링크), 블로그 목록, 홈(최근 글)을 본다. 데스크톱과 모바일(375px) 폭 모두 확인하고(가로 스크롤 없음), 글 보기 스크린샷을 보고에 남긴다.
  - 본문 이미지는 지연 로딩이라, 숨겨진 창이나 개발 서버의 첫 요청에서는 빈칸으로 보일 수 있다. 빈칸이면 이미지 요소의 `naturalWidth`와 이미지 주소의 응답(200, `image/webp`)으로 확인한다.

## 7. 커밋과 push

- 이 저장소의 `CLAUDE.md`를 따른다. 글 폴더(`src/content/blog/`)와 데이터 파일(`src/data/`)만 바꾼 커밋은 콘텐츠 예외로 main에 바로 push한다. 코드·설정·문서가 하나라도 섞이면 예외가 아니므로 멈추고 사용자에게 알린다.
  - 8단계가 아직 완료로 표시되지 않았어도 실제 콘텐츠는 main에 push한다. 첫 push가 8단계의 운영 흐름 확인이다(`docs/memory.md`). 확인을 마치면 8단계를 완료로 표시하는 일은 작업 브랜치에서 문서로 한다.
- 시작할 때 main에 있고 작업 폴더가 깨끗한지, 원격과 같은지(`git pull --ff-only`) 본다. 아니면 멈추고 알린다.
- 이번에 만든·고친 파일만 지정해 스테이징한다. 커밋 메시지는 영어로 쓴다(예: `Add a post about ...`).
- **push는 사용자가 확인한 뒤에 한다.** 커밋할 파일 목록과 글 주소(두 언어)를 보이고 확인받는다. 공개되는 작업이라 다른 확인으로 대신하지 않는다.
- `pre-push` 훅의 검사를 건너뛰지 않는다(`--no-verify` 금지).

## 8. 배포 확인

- push한 커밋의 GitHub Actions 실행을 찾아(`gh run list --commit <sha>`) 끝날 때까지 기다린다(`gh run watch <id> --exit-status`). 오래 걸리면 백그라운드로 실행한다.
- 운영 주소의 두 언어 글(`https://mivomad33.dev/blog/<slug>/`, `https://mivomad33.dev/en/blog/<slug>/`)이 200으로 열리고 제목이 맞는지 본다. 바로 404면 잠시 뒤 다시 본다(배포 반영이 늦을 수 있다).
- 실패하면 실패한 작업의 로그(`gh run view <id> --log-failed`)로 원인을 알리고 고칠 방법을 제안한다.

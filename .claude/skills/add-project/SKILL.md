# 프로젝트를 포트폴리오와 글로 넣기

입력은 완성한 프로젝트의 경로다(인자로 받는다. 없으면 묻는다). "포트폴리오만", "글만"이라고 하면 그것만 한다. 기본은 둘 다다.
결과는 이 저장소의 포트폴리오 항목(`src/data/portfolio.yaml`)과 글 폴더(`src/content/blog/<slug>/`의 `ko.md`, `en.md`, `images/`)다.
흐름은 하나다: **살펴보기 → 질문과 구성안(멈춘다) → 쓰기 → 이미지 → 검증 → 보고와 push 확인(멈춘다) → push·배포 확인.**

목표는 처음 온 사람이 **무엇을 왜 만들었고, 무엇을 어떻게 정했는지** 알게 하는 것이다. 기능 소개서가 아니라 만든 사람의 결정 이야기다.
예시는 Senseful이다(`src/content/blog/building-senseful/`와 `portfolio.yaml`의 Senseful 항목). 문체와 원칙을 참고하고, 섹션 구성은 따라 하지 않는다. 매번 같은 구성이면 글이 비슷해지기 때문이다.

글의 형식·내용 원칙·문체·영어 글·이미지 넣기·검증·커밋·배포 규칙은 [공통 규칙](../shared/post-writing.md)을 따른다. 이 파일에는 프로젝트를 재료로 쓰는 데 필요한 것만 둔다.

결정과 이유는 [변경 6 문서](../../../docs/changes/6-add-project-skill.md)에 있다. 공통 규칙으로 옮긴 것은 [변경 7 문서](../../../docs/changes/7-write-post-skill.md)에 있다.

## 1. 살펴보기

파일 목록만 보고 짐작하지 않는다. 원본 프로젝트는 **읽기만** 한다(파일을 고치거나 커밋하지 않는다).

- 이 저장소: `CLAUDE.md`(커밋·브랜치 규칙), `docs/design.md`의 데이터 파일 형식, `docs/memory.md`, [공통 규칙](../shared/post-writing.md), Senseful 예시. 이미 같은 프로젝트의 항목이나 글이 있는지 본다(있으면 새로 만들지 않고 고친다).
- 원본의 규칙과 소개: `CLAUDE.md`, `AGENTS.md`, README(두 언어면 둘 다).
- **원본의 결정 기록**: 개요·설계·단계 문서, 메모, 명세서, 점검·평가 결과, 홍보 초안. 글의 좋은 재료(왜 그렇게 정했는지, 뺀 안, 검증한 숫자, 한계)는 대부분 여기 있다. 코드는 기능과 기술 스택을 확인하는 데 쓴다.
- 공개 여부: 저장소(`gh repo view <소유자>/<이름> --json visibility,owner`)와, 각 문서가 공개 저장소에 올라가 있는지(`git ls-files`, `git check-ignore`). 무시 목록에 있거나 별도 저장소인 문서는 **비공개**다.
- **원본이 공개 문구에 대해 정한 것**: 원본의 메모·명세서에 "README에 쓰지 않는다"처럼 정한 것(경쟁 서비스 이름, 실명 등)이 있으면 글에도 그대로 따른다. 다르게 하려면 2장에서 묻는다.
- **진행 상태**: 단계·계획 문서에서 끝나지 않은 단계와, 개요의 성공 기준을 확인했는지 본다. "완성"이라고 받았어도 목표를 아직 확인하지 않았으면 글에 이룬 것처럼 쓰지 않는다. 다만 아직 이루지 못한 목표나 남은 일을 따로 섹션으로 쓰지도 않는다(사용자 선호, 2026-10-24: 시험 글의 "아직 남은 것" 섹션을 필요 없다며 지웠다).
- 운영 주소, 로그인 없이 볼 수 있는 데모, 화면 언어, 배포처.

읽으면서 **사실 메모**를 세션 임시 폴더에 남긴다. 글에 쓸 만한 사실마다 출처(파일 경로)와 공개·비공개를 적는다. 쓰기 단계에서는 이 메모에 있는 사실만 쓴다.

## 2. 질문과 구성안

**쓰기 전에 사용자 확인을 받는 곳은 여기 한 번이다**(다른 한 번은 7장의 push 확인이다). 답을 받기 전에는 파일을 쓰지 않는다. 한 메시지에 구성안을 보이고, 정할 것은 묻는 도구로 한 번에 묻는다(도구가 받는 질문 수를 넘으면 이어서 묻는다). 질문마다 선택지와 영향을 짧게 적고 추천안을 앞에 둔다.

구성안(메시지 본문):

- 중심 이야기 한두 줄: 이 글이 무엇에 대한 이야기인지(예: Senseful은 "무엇을 Claude에게 맡기고 무엇을 맡기지 않았나").
- 제목(한국어), slug, 설명(한두 문장).
- 섹션 목록과 섹션마다 쓸 핵심 사실(사실 메모에서).
- 포트폴리오 설명 초안(한국어)과 링크 목록.
- 넣을 화면 목록과 찍을 곳(데모, 시드 데이터 등).

물을 것(해당할 때만. 문서에 이미 답이 있으면 묻지 않고 그대로 따른 뒤 보고에 적는다):

1. **만든 동기**: 개인 경험(무엇이 불편했는지 등)은 문서에 없으면 사용자만 안다. 문서에 있으면 그 내용을 구성안에 적어 확인만 받는다.
2. **중심 이야기**: 후보가 여럿이면 2~3개를 내고 추천안을 앞에 둔다.
3. **비공개 출처의 사실**: 비공개 문서에서만 나온 사실(평가 숫자, 비용, 내부 결정)을 묶음별로 보이고 공개해도 되는지 묻는다(여럿 고르기). 글에 쓰면 공개되기 때문이다.
   - 판단을 맡기면: 결정과 그 이유, 설계 때의 비용 예상(예상이라고 밝힌다)은 쓴다. 남용에 쓰일 수 있는 운영 값(한도 숫자, 최악의 비용), 내부 보안 세부, 테스트 개수 같은 진행 기록, 개인 정보는 뺀다. 무엇을 쓰고 뺐는지 보고에 적는다.
4. **GitHub 링크**: mivomad33 계정의 공개 저장소면 묻지 않고 넣는다. 다른 계정이거나 비공개면 넣을지 묻고, 답이 없으면 넣지 않는다(다른 계정 이름이 공개 사이트에 드러나지 않게 하기 위해서다). 비공개 저장소는 링크해도 열리지 않는다는 영향을 적는다.
5. **로그인이 필요한 화면**: 데모 없이 로그인해야만 보이는 화면을 넣으려면 사용자가 찍어 줘야 한다. 넣을지와 누가 찍을지 묻는다.
6. 이미 포트폴리오에 항목이 있으면: 그 항목을 고칠지, 글만 더할지.

묻지 않고 정할 것: 섹션 이름, 문장, 이미지 구성과 크기, 영어 문구, 게시일(오늘), 커밋 방식(이 저장소의 `CLAUDE.md`).

## 3. 글 쓰기

[공통 규칙](../shared/post-writing.md)의 형식·내용·문체·영어 글을 따른다. 사실 메모는 1장에서 만든 것이다. 프로젝트 글에 더하는 것:

- 문서와 코드가 다르면 코드를 따르고 보고에 적는다.
- 결정의 이유는 원본 문서에 적힌 것만 쓴다.
- 흐름은 대체로 문제(왜 만들었나) → 무엇을 하는 앱인가(대표 화면) → 핵심 결정 몇 개 → 만든 방식·기술 → 써 보기(링크) 순이 읽기 쉽지만, 고정하지 않는다.
- 기술 스택은 나열을 짧게 하고, 고른 이유가 있는 것만 설명한다.
- 맨 끝에 사이트·데모·코드 링크와, 화면 언어나 베타 같은 이용 조건을 둔다.

## 4. 포트폴리오 항목

- `src/data/portfolio.yaml`의 **맨 위**에 넣는다(파일 머리 주석의 규칙). 이미 있으면 그 항목을 고친다.
- `name`: 프로젝트 이름(두 언어가 같으면 한 값).
- `description`(`ko`, `en`): 두세 문장. 무엇을 하는지 → 핵심 아이디어 한 가지 → 기술 스택과 배포처. 글과 같은 사실만 쓴다.
- `links`: 있는 것만, 이 순서로.
  - 사이트(`ko: 사이트`, `en: Site`), 운영 주소와 따로 데모가 있으면 데모(`ko: 데모`, `en: Demo`)
  - GitHub(2장 4의 규칙)
  - 글을 썼으면 만든 이야기(`ko: 만든 이야기`, `en: Write-up`, `url: /blog/<slug>/`). 사이트 안 주소는 한국어 경로로 한 번만 적는다(영어 페이지에서는 자동으로 `/en`이 붙는다).
- "글만"이면 포트폴리오는 건드리지 않는다. 다만 항목이 있고 만든 이야기 링크가 없으면 더할지 2장에서 함께 묻는다.

## 5. 화면 이미지

- **가짜·시드·데모 데이터 화면에서만 찍는다.** 실제 개인 데이터가 있는 화면(로그인한 운영 화면, 개인 데이터가 든 개발 DB)은 찍지 않는다. 로그인해야만 보이는 화면은 2장 5의 답을 따른다.
- 내장 브라우저로 운영 사이트나 데모를 열어 찍을 화면과 상태를 고른다. 파일로 저장하는 일은 Playwright로 한다(내장 브라우저의 스크린샷은 파일로 남지 않는다). 이 저장소와 원본의 의존성은 바꾸지 않는다.
  - 원본 프로젝트에 Playwright가 있으면 세션 임시 폴더에 Node 스크립트(`.cjs`)를 두고, `createRequire('<원본>/package.json')`으로 원본의 것을 불러 쓴다. pnpm 프로젝트에서는 직접 의존성만 찾을 수 있어 `playwright`가 아니라 `@playwright/test`를 불러야 할 때가 많다. 원본에 없으면 `npx --yes playwright@<버전> screenshot`을 쓴다.
  - 브라우저 언어를 화면 언어에 맞춘다(`chromium.launch({ args: ['--lang=ko-KR'] })`). 맞추지 않으면 날짜 입력 같은 기본 컨트롤이 영어로 찍힌다.
  - 휴대폰 화면은 폭 390, `deviceScaleFactor: 2`로 찍는다. 데모처럼 쿠키로 들어가는 화면은 같은 브라우저 문맥에서 데모 주소를 먼저 연 뒤 이동한다.
- 여러 장은 한 장으로 합친다(Senseful의 `images/screens.jpg`: 휴대폰 폭 화면 세 장을 나란히, 1640×1125). 세션 임시 폴더에 화면을 나란히 놓은 HTML(화면마다 폭 500px, 간격·여백 30px, 연한 회색 배경, 둥근 모서리와 옅은 테두리)을 만들고, 그 묶음 요소를 Playwright로 jpg(품질 85)로 찍는다. 이렇게 하면 세 장이 약 1630×1150이 된다.
- 화면은 글의 이야기에 맞는 것을 고른다(예: 업로드 흐름이 중심이면 업로드 화면을 넣는다). 표처럼 휴대폰 폭에서 잘리는 화면은 피한다.
- 개발 서버에서 찍으면 개발 전용 표시(개발 도구 버튼 등)는 찍는 순간에만 숨긴다. 원본 코드를 바꾸지 않는다.
- 크기, 눈으로 확인하기, 글에 넣는 방법은 [공통 규칙](../shared/post-writing.md)의 이미지 넣기를 따른다. 찍은 화면은 로딩 중 화면이 아닌지도 본다.

## 6. 검증

[공통 규칙](../shared/post-writing.md)의 검증을 모두 통과시킨다. 프로젝트에 더하는 것:

- 사실 대조에 포트폴리오 항목도 넣는다. 비공개 출처의 사실은 2장에서 허락받은 것만 있는지 본다.
- 화면 확인에 포트폴리오 페이지, 홈의 최근 포트폴리오, 포트폴리오의 만든 이야기 링크가 그 언어의 글로 가는지를 더한다.

## 7. 보고와 push 확인

짧게 알리고, push를 확인받는다.

- 만든 것: 글 제목·주소(두 언어), 포트폴리오 항목, 이미지.
- 스스로 정한 것과 문서를 따라 묻지 않은 것.
- 검증 결과(항목마다 통과 여부)와 글 보기 스크린샷.
- 원본 프로젝트에 하면 좋을 일(README에 글 링크 더하기 등). 이 스킬은 원본을 고치지 않는다.
- 사용자가 할 일: 글을 읽고 문장·사실 확인, push 승인. 고칠 곳을 말하면 고치고 다시 검증한다.

## 8. 커밋, push, 배포 확인

push 승인을 받으면 [공통 규칙](../shared/post-writing.md)의 커밋과 push, 배포 확인대로 한다. 원본 프로젝트에는 커밋하지 않는다. 배포 결과(운영 주소 두 개)를 알리고 끝낸다.
